<Update label="[Release date]" tags={["CLI", "Security"]} description="A task channel (Preview)">
  ## Your computer and a box can pass tasks instead of notes

  Questions, answers and status between you and an agent on a box now travel as tasks with a state, an acknowledgement and an audit record, signed and sealed so they cannot be forged, replayed or reordered. **Preview:** built and tested with fakes and a real two-endpoint run of the program; not yet run against a real box, and it leaves Preview when that proof passes.

  - **A box runs the channel as a user of its own**, so an agent on the box can ask and answer through it but cannot read its keys. On your computer the channel's private keys are kept in your keychain, never in a file. A peer's words are always shown as untrusted (`--for-model` fences them for a model), a cancel is a request the other side decides, and the first contact finishes in one `ozbox tasks sync`.
  - **`ozbox tasks`** sets up the two sides, sends a task, shows your inbox, answers, cancels, and explains why a task is stuck (`ozbox tasks why`).
  - **A message can ask and never grant.** Saying "approved" in a task changes nothing, and text that looks like a key is refused on both sides and never stored.
  - **Acts that need an approval are refused by name** until the passkey approval path exists, and a Production act is refused outright.
  - A closed laptop is a normal state: the task waits and is delivered when you next sync.
  - See [A task channel](/use-cases/task-channel) and [ADR 0044](/adr/0044-the-agent-mesh-a-task-channel-where-a-message-can-ask-and-never-grant).
</Update>

<Update label="[Release date]" tags={["CLI", "Security"]} description="Main as the hub (Preview)">
  ## `main` can hand a task to a worker over a channel of its own, and a worker is never given Production

  Until now `main` reached a worker through your computer's connection. This release adds the first part of a route that does not: `task_start` takes `transport: hub`, the task goes to the worker as a signed, sealed message, and `task_status` shows what the worker reported. **Preview:** built and tested with fake boxes only; no box has a hub yet, and it has not run on a real cloud box.

  - **On a box with no hub, `transport: hub` is refused by name** and the default `ssh` route works exactly as before.
  - **A worker is never given a Production key.** The hub refuses it, the worker refuses it again, and the off-box issuer refuses a worker. No setting turns this off; it comes back later, approved at your computer.
  - **A task never names keys.** A conductor that tries is refused, and the attempt is recorded.
  - Every hand-off and refusal is in the audit record by name, never by value.
  - **The hub's daemon and how a worker joins.** `ozbox-hubd setup <box-id>` sets up the hub on `main` and `ozbox-hubd self-test` checks it. A worker joins only with a one-use invite, an attestation from a registrar your setup pinned and proof that it holds the attested key, and the hub plans the enrolment before it applies it. A Production box, `main` itself, an unknown box or a replayed attestation is refused. Messages are sealed to each worker's attested key and signed by keys only the secrets service holds. No worker can enrol on a real box until a registrar exists.
  - **The registrars that vouch for a worker.** On AWS a worker proves it is the instance it claims with the identity document AWS signs; for Hetzner and machines you own, your own computer signs after you confirm a plan (`ozbox hub attest`, refused on a box). `ozbox hub repin` pins or rotates which registrars the hub trusts, and `ozbox hub registrar-key` makes your computer's key. Not yet: the AWS service that calls the AWS check is not deployed, and no real AWS document has been verified.
  - See [Orchestrating a fleet](/use-cases/orchestrating-a-fleet) section 11 and [ADR 0042](/adr/0042-main-as-the-hub-workers-reached-over-a-sealed-channel-keys-sent-only-by-name-and-every-approval-comes-back-to-main).
</Update>

  ## Oz Box 0.2.0-beta.3: AWS boxes keep their secrets, backups and dashboard through upgrades

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="AWS boxes with secrets of their own">
  ## A box's own secrets now load from Parameter Store

  A box set up with secrets of its own in AWS Parameter Store could not load them: the loader used the AWS command, which the box image does not carry, and the only sign was a failed unit. The secrets never appeared.

  - **The loader reads Parameter Store itself**, with the box's own role. Nothing needs installing on the box, and which parameters it reads (its own path, non-production only) is unchanged.
  - **The box's self-test now says it.** When a box that declares secrets could not load them, the self-test fails with `box_secrets_loaded` and says where to look, instead of the box looking well.
  - **Known limit.** A box whose secrets are in OpenBao still needs the `bao` program on it.

  **How to get it.** `ozbox upgrade <box>` to the release that carries this. See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).
</Update>

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="AWS boxes set up for the fleet's KMS key">
  ## A box set up for the fleet's KMS key now starts its secrets service

  A box set up for the fleet's KMS key could not start its secrets service. Every start said the key that protects the box's secrets was not available, and no secret could be read or saved. The box image does not carry the AWS command the service used to reach the key.

  - **The secrets service reaches the key itself**, with the box's own role. Nothing needs installing on the box, and the key's access rules (the role may use the key only for its own box) are unchanged.
  - **The box's self-test now says it.** When a box set up for KMS cannot use its key, the self-test fails with `secrets_key_usable` once the key has been failing for three minutes (the service keeps count across its restarts), names the KMS key and lists what to check; sooner than that, or when the service has not written its state yet, it says it could not verify, never a pass. A store that cannot be opened for good is pointed at `recover-secrets` or `adopt-fleet-key`, not at the network.
  - **Nothing is lost on the way.** A store waiting on its key is kept as it was and opens again once the key works. See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).

  **How to get it.** `ozbox upgrade <box>` to the release that carries this.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="Secrets service outages">
  ## An upgrade plan no longer says "kept" about a store it has not checked, and you can still commit while the secrets service is down

  **The upgrade plan tells the truth about the secrets store.** For a box on your fleet's KMS key, `ozbox upgrade` used to say the store was kept because the box's record named the key, even when the box's secrets service could not open its store. The plan now asks the box itself and says one of four things: kept, will be lost, already cannot be opened (and how to start a new store, as part of the upgrade with `--accept-new-secrets-store` or beforehand with `ozbox admin <box> -- recover-secrets`), or unknown because the box could not be asked. It only says a store cannot be opened when no copy of its key is held anywhere: if your computer's keychain or the box's vault holds one, it says the store is not lost, and that `--accept-new-secrets-store` sets the old store aside (never deleted) and starts a new one, so the old one can be reopened later from the held key. Unknown is never "kept". See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).

  **Commits are not blocked while the secrets service is down.** Before, every commit on the box was stopped until the service came back, so work could not be saved. Now a commit is still checked for private keys, provider keys, signed tokens, passwords in addresses and `.env` files. A clean commit goes through, with a note that stored secrets were not compared; nothing is lost. A commit that looks like it holds a key is stopped, and the message says so. A push is held until the service is back, because that is what leaves the box, and the message says how to bring the service back. See the [CLI reference](/cli-reference).
</Update>

<Update label="November 16, 2026" tags={["CLI", "Dashboard"]} description="Backups through an upgrade">
  ## An upgrade no longer leaves a box quietly un-backed-up

  An upgrade replaces a box's system disk. If the box backed up `/work` to a repository, nothing told you afterwards whether those backups still worked, and settings you had made on the box itself could be gone.

  - **Your backup settings come through.** The repository's password and keys stay in the box's encrypted secrets store, which an upgrade keeps when the store can be opened on the new machine, so backups you set up on the box itself no longer depend on this computer holding anything. What is backed up and how often, if you changed it on the box, is kept by root on `/work` and applies on the new system disk.
  - **The upgrade checks that backups work.** After the self-test it asks the box whether backups are configured and whether the repository answers, and the report says so. A box whose backups were set up and are not working now fails its self-test, and the upgrade ends with an error naming what to run. A box that never had backups is not failed for it.
  - **If a new secrets store was started** (`--accept-new-secrets-store`), backups stop until their credentials are sent again. The upgrade puts them back from this computer when it holds them; otherwise it says **BACKUPS HAVE STOPPED** and the command: `ozbox backup credentials <box>`.
  - **A box that already has its credentials keeps them.** The upgrade no longer sends this computer's copy over a box's own.
  - **New command:** `ozbox backup credentials <box>` sends the repository's password and keys from this computer's secret store to a box. They are never printed.
  - **Turn off backups on a box, on purpose.** In the box's **Backups** tab choose **Turn off backups on this box**, or run `ozbox backup off <box>`. It says what stops, removes the repository credentials from the box and switches its schedule off, so the self-test and an upgrade stop expecting backups and the next slot does not send the credentials back. Backups already made stay where they are.
  - **A busy repository is not an empty one.** While a backup is pruning, listing a box's backups says it is busy instead of showing none, and the dashboard keeps the last list on screen.
  - **A box that is still starting is not "stopped".** If the box's secrets service is not up yet, the report says backups were not checked and sends nothing, instead of saying they stopped. The repository check has a time limit, and the self-test shows the last answer and its age while a new check runs.
  - **Real-world exclude settings are kept.** Patterns such as `*.tmp` and `node_modules` in the `[backup]` section no longer stop the box from remembering that backups were set up.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Dashboard"]} description="Hosted dashboard">
  ## An upgrade puts your hosted dashboard back, with its tunnel token

  Installing the dashboard on a box with a tunnel token used to leave that token only on the box. An upgrade that started a new secrets store lost it, and the dashboard stayed down until you had the token again.

  - **This computer keeps the token.** `ozbox dashboard install ... --token-stdin` now keeps the token in this computer's keychain (never in a file, never shown), together with the address, people and tunnel you gave it.
  - **`ozbox upgrade` puts the dashboard back** after it replaces the box's machine, and its report has a **Dashboard** line: put back, not put back (with the one command to run), or not installed.
  - **When the box asks for your approval of the token,** the upgrade does not make it for you. Run `ozbox dashboard restore <box> --approve-with-laptop-key`: it uses the token this computer kept and approves that one token with the key this computer pinned when the box was made.
  - **`ozbox dashboard restore <box>`** brings the dashboard back by hand; **`ozbox dashboard install --token-from-keychain`** reuses the kept token; **`ozbox dashboard forget <box>`** removes what this computer kept.
  - **A dashboard installed before this release** is kept the next time you install it with `--token-stdin`. **Not yet run on a real box.**

  See [run the dashboard on a box](/use-cases/coding-from-anywhere) and [keeping boxes healthy](/use-cases/keeping-boxes-healthy).
</Update>

<Update label="November 16, 2026" tags={["Dashboard"]} description="Dashboard stays responsive">
  ## The dashboard no longer freezes while your cloud or a box is slow

  With a real fleet, the Fleet and Boxes pages could stop with "This page could not ask the server what it is". Listing your boxes in the cloud and asking each one how it is doing can take a long time, and while it did, every other request waited behind it.

  - **Pages load while the cloud is slow.** `ozbox serve` answers what the server is, the dashboard's files and sign-in at once, however long a box takes to reply.
  - **The box list shows what was last read, and says so.** When your cloud is slow, the Fleet and Boxes pages show the last list with how old it is and that it is being read again, instead of an error. The first read after `ozbox serve` starts says it is reading your boxes and can take up to half a minute.
  - **A box that does not answer is reported as not reached** after a few seconds. The other boxes and the list are not held up for it, and asking again does not pile more questions on it.
  - **A busy server says so.** If far more boxes are being asked about at once than the server will take on, the extra requests are told to try again in a moment instead of waiting without end.
  - **A page that could not reach the server brings itself back** as soon as the server answers, without pressing Try again.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="AWS operator permissions">
  ## `ozbox init` now gives you the complete operator policy, including what `ozbox adopt-fleet-key` needs

  Setting up again on an account made by an earlier release did not add the permissions `ozbox adopt-fleet-key` needs, so the command failed with "Systems Manager refused" until an administrator pasted them in by hand.

  - **One complete policy, written every run.** `ozbox init` writes the whole operator policy for your account, region and fleet to `operator-policy.json` in its working folder and prints the path, whether or not anything else changed. It already includes the three Systems Manager statements the adopt command needs.
  - **It tells you if your daily sign-in is out of date.** When your config names the daily profile, `ozbox init` checks, read only, whether that sign-in can read a Systems Manager command's result. If not, it prints the three missing statements and the one step: an administrator replaces the daily role's inline policy with the file. Applying it twice is safe.
  - **`ozbox init` still does not change the operator role itself.** The setup sign-in has no right over the operator's permissions, so a person who could rewrite them could not widen them. Nothing is widened: still no `kms:` action, and still no first tag on an existing disk. See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).
</Update>

<Update label="November 16, 2026" tags={["CLI"]} description="ozbox upgrade and create">
  ## `latest` now means the newest image whose signed release verifies

  `ozbox upgrade <box>` (and `ozbox create` with no image) used to take the newest Oz image it could see. When that image's release had not been published or signed yet, the upgrade was then refused, even though the release before it was fine.

  - **A newer image that cannot be verified is passed over** for the newest one that can: its release was never published, does not list the image for your region, or is a pre-release a stable program does not use.
  - **The plan says which ones were passed over,** one line each, with the reason.
  - **If no image verifies, the command refuses** and names the two ways forward: `--image <id>`, or `--allow-unverified-image`.
  - **Naming an image with `--image` works as before.** A check that could not be made (a network or signature-tool failure) still stops the command instead of falling back to an older image.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Dashboard", "Security"]} description="0.2.0-beta.2: declarations that fit a real app, safer upgrades">
  ## Oz Box 0.2.0-beta.2: declarations that fit a real app, safer upgrades

  - **A real app's command declaration saves.** Declarations are stored as records with a 256 KB limit, so a Next.js app's pins fit, and a refused save no longer uses up your approval code.
  - **Importing keys is easier and honest.** `--allow-live-all` allows every production-looking key in a file behind one typed confirmation, and the report accounts for every line.
  - **An upgrade that could lose a box's secrets store keeps the old system disk** as an encrypted snapshot first, so the old store stays recoverable, and says so loudly in the plan.
  - **The box list no longer closes a menu you just opened** when the server's details arrive late.
  - **macOS programs are released again**, built on a current runner and checked by asking the program which dashboard it carries.

</Update>

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="AWS boxes made by 0.1.x">
  ## `ozbox adopt-fleet-key` no longer fails half way on a box made by 0.1.x

  A box made by `0.1.x` has a system disk that was never tagged. Moving its secrets store to your fleet's KMS key tried to tag that disk, the permissions `ozbox` runs with cannot put a first tag on an existing disk, and the command failed after it had already marked the box as moving. An administrator had to tag the disk by hand before it could go on.

  - **The move no longer touches the system disk's tags.** It goes through on a `0.1.x` box with no administrator step. A box's system disk is still tagged when it is created, and an upgrade creates a new one.
  - **A change that would still need a first tag stops before anything is changed.** `ozbox` names the disk and prints the two commands an account administrator runs once, with their own sign-in: check the disk belongs to the box's machine, then `aws ec2 create-tags`. Run the same `ozbox` command again afterwards. The check covers every step of the move, so a box an earlier run left half moved is stopped on the way out too, and nothing is applied.
  - **The permissions did not widen.** Neither the daily `ozbox` sign-in nor the setup sign-in can tag an existing disk as Oz Box's, so a disk it did not make cannot be claimed and then changed. See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).
</Update>

<Update label="November 16, 2026" tags={["CLI", "Security"]} description="0.2.0-beta.2: a box moved to your fleet's key starts its secrets service">
  ## A box upgraded onto your fleet's KMS key now starts its secrets service

  Upgrading a box with a file-kept secrets key onto the fleet's KMS key (`ozbox upgrade <box> --accept-new-secrets-store --use-fleet-key`) could leave its secrets service retrying forever, with the old store unopenable and nothing set aside. This release fixes it.

  - **The box says so.** A store the box can never open is now reported as exactly that, not as a service that is merely restarting.
  - **The upgrade finishes the job.** With `--accept-new-secrets-store`, the old store is set aside (renamed, never deleted), with the approval of this computer's pinned key, and a new one starts on the fleet's key. The plan for `--use-fleet-key` says so before you confirm.
  - **`ozbox admin <box> -- recover-secrets` handles it too**, behind the same approval. It still refuses a store that can be opened and a service that is only restarting, and tells you which state it found. See [Keeping boxes healthy](/use-cases/keeping-boxes-healthy).
  - **A box already stuck on 0.2.0-beta.1** is told what to run: upgrade it to an image from 0.2.0-beta.2 or later with `--accept-new-secrets-store`.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Dashboard", "Security"]} description="0.2.0-beta.1: fixes from the first real upgrade">
  ## Oz Box 0.2.0-beta.1: fixes from the first real upgrade

  Upgrading a real box to 0.2.0-beta.0 turned up problems in setup and upgrade. This release fixes the ones a box needs, and its image carries them.

  - **A box's secrets store can move to your fleet's KMS key** even when only the disks' tags change.

Upgrading it starts a new store (`--accept-new-secrets-store`): put the keys back with `ozbox secrets import` afterwards, then run `ozbox adopt-fleet-key` so later upgrades keep the store. <Update label="November 16, 2026" tags={["CLI", "Security"]} description="Declarations of a real application">
  ## A real application's command declaration now saves, and a refused one no longer uses up your approval code

  `ozbox env policy set` refused a realistic declaration (a service, a folder pin for each package a Next.js build traced, a few file pins and a tool, about 7 KB) with "the value is too long", because it was stored like a short key. And when the box refused a save, your single-use approval code was already spent, so you had to make another by hand each time.

  - **Declarations up to 256 KB are kept as they are**, with the same protection as before. A declaration saved by an earlier version still loads, and is replaced by the new form the next time you save. Keys and tokens keep their own, shorter limit.
  - **A declaration that is too big says so**: it names its size and the limit. The [guide](/use-cases/secure-agent-workspace) lists every limit of a declaration.
  - **Your computer checks first.** The declaration's rules (including names a command cannot set, such as `NODE_OPTIONS`) and its size are checked before anything is sent, and the box checks them again before it looks at your approval code.
  - **An approval code is used up only by a save that happened.** If the box cannot save, the same code works for your next try; a save that went through spends it, and it cannot be used twice.
  - **An older box is not sent what it would refuse.** If a declaration is too big for a box that has not been upgraded, your computer says so before it sends anything, and your approval code is not used. Run `ozbox upgrade` on the box, or make the declaration smaller.
  - A box running this version stores declarations in the new form. If you later move a box back to an earlier version, that version reads a stored declaration as damaged, so set your declarations again after a downgrade.
  - `ozbox secrets status` no longer counts a declaration among the encoded values.
</Update>

<Update label="November 16, 2026" tags={["CLI", "Dashboard", "Security"]} description="Upgrading an old box no longer destroys the key to its secrets">
  ## An upgrade that could lose your secrets store keeps a copy of the old system disk first

  A box made on `0.1.x` keeps the key to its secrets store in a file on its system disk, and an upgrade replaces that disk. The upgrade could not prove the key survived, so it refused unless you accepted a new, empty store, and accepting it destroyed the old key for good: every key had to be entered again, and the old store could never be opened.

  - **On AWS, the upgrade now keeps a copy of the old system disk by default** when it cannot show the store's key survives. It is an encrypted snapshot, tagged so it is never taken for a backup of `/work`, taken before anything is stopped. If it cannot be made, nothing is changed.
  - **The plan says it in words, before you confirm**: what would be lost, that a copy is kept, and the commands to run afterwards (`ozbox secrets import … --box`, then `ozbox adopt-fleet-key`). The snapshot's id is in the report, and `ozbox backup list` shows it.
  - **Reopen the old store from it** with the steps in [Keeping boxes healthy](/use-cases/keeping-boxes-healthy). That guide also says when to delete the snapshot: it holds the old key, it is billed like any snapshot, and nothing deletes it for you.
  - **The copy goes with the box.** `ozbox destroy` deletes the copies of old system disks the box's upgrades kept, because ozbox cannot list them once the box is gone and each holds an old key; the plan lists them. `--keep-old-system-disks` keeps them, and then they are yours to delete in AWS. Each upgrade takes its own copy, so a retried upgrade leaves another, and the report names the one it took. `ozbox upgrade` takes the copy first and waits up to thirty minutes for it (`snapshot_wait_minutes` under `[aws]`); a copy that is not complete in time stops the upgrade before anything changes, names the snapshot, and finishes by itself.
  - **`--no-pre-upgrade-snapshot`** turns the copy off, and the plan then says the old store can never be opened. No copy is taken when the store is kept, already lost or empty.
  - **Not run on a real account yet.** Tested in CI against a simulated account and box. The steps to read the old key back from the snapshot are written down, and the part on the box is checked by a test; the part in AWS has not been run.
</Update>

<Update label="November 16, 2026" tags={["CLI"]} description="AWS setup">
  ## `ozbox init` now takes over what is already in your account instead of making it a second time

  On an account you set up with an earlier version of Oz Box (or by hand), `ozbox init` could look clean and then fail, or make a copy: a second key, or a document or policy that "already exists".

  - **It looks first.** For the fleet's secrets key and its alias, the adopt command's document and the boxes' Session Manager policies, init checks whether they are already there, using only read access.
  - **The plan says "Adopt existing".** You see each one, with its id, instead of a create. Nothing is created for it, and anything that differs from what Oz Box would make is listed below as a change.
  - **Only what Oz Box made.** It must carry the `ozbox-managed` tag. Anything else with the same name is refused, with the reason, and nothing is changed.
  - **Never replaced or removed.** A plan that would replace or delete something it adopted is refused before anything runs.
  - **If it cannot tell, it stops.** A check that is denied or fails is reported; init never guesses that something is missing.
  - **Not yet.** The network and the off-box issuer are not adopted: on an account whose network was made another way, decline that step and use the one you have. **Not yet run against a real AWS account.**
</Update>

<Update label="November 16, 2026" tags={["CLI"]} description="Fleet-key move and self-test">
  ## `adopt-fleet-key` no longer refuses a box only because its tags change, and the self-test stops reporting a one-time service that had nothing to do

  - **`ozbox adopt-fleet-key`** moves a box to your fleet's key by adding tags to its resources. It refused when the only difference on the box's system disk was those tags. Tags on the system disk may now change; a change to its size, type, encryption, key, speed or delete-on-termination is still refused, and nothing is changed when it refuses.
  - **The self-test** no longer reports "enabled but not running" for a one-time service that finished, or that did not start because its start condition was not met (for example, resuming a session after an upgrade that left nothing to resume). A service that should keep running and does not, a service whose last run failed, and a user manager that never started its services are still reported.
</Update>

<Update label="November 16, 2026" tags={["CLI"]} description="Adopt command setup">
  ## `ozbox init` can now set up the adopt command from an installed program

  Setting up the adopt command during `ozbox init` stopped with "no file exists" for a file named `adopt-document.yaml`, because the installed program did not carry it. The program now carries every data file its setup modules read, and a check on every build fails if a module reads a file the program leaves out. Nothing is needed from you: a new program unpacks its own fresh copy of the setup files next to the old one, and the old copy is never reused.

  - **Checked on a source build.** Running `ozbox init` end to end from an installed release is still to come.
</Update>

<Update label="November 16, 2026" tags={["CLI"]} description="AWS setup on an account that already has boxes">
  ## `ozbox init` no longer plans a second network, stops when you skip a step, or hides your config

  Running `ozbox init` on an account that already had a box planned a new private network (about $33 a month for its NAT gateway) even though your configuration named a subnet, and answering no ended the whole setup, so the secrets key, the adopt command and the box policy could never be made. <Update label="November 15, 2026" tags={["CLI","Security"]} description="The commit barrier">
  ## The commit barrier stops holding ordinary files, says where, and waits for a person

  - **A public value is not a key.** A web address or a value of a variable that is meant for the browser (`NEXT_PUBLIC_*`, `VITE_*`, `EXPO_PUBLIC_*` and the like) no longer holds a file, and naming such a variable in code or in a document never does. An address with a user name and password in it, or a chat webhook or private link, is never taken as public, and neither is an address with a query (`...:443?transport=tcp`): that one is held like a key, so keep the query in its own variable or let the change through with an override. A real key under such a name is still held. A bare `PUBLIC_*` name is not taken as public (SvelteKit and Astro projects mark their values when they import them with `--public`).
  - **Short values and ordinary words.** A stored value shorter than 12 characters (a region, a port, `true`) no longer holds every file that says it. A long hyphenated word such as `risk-assessment-for-the-plan` is no longer mistaken for a key.
  - **A hold says the file, the line and the rule.** It never prints the value, or the name of the secret it matched.
  - **On a box, a held commit or push asks a person.** It files a request you decide on the Approvals page, and the commit goes through once you approve that exact change. Change it after approving and it is refused.
  - **A code is for one change.** A code made with `ozbox secrets approve --scope guard-override --project ... --env ...` passes the change it was made for and no other. The hold prints the two values.
  - **Large pushes are read, not refused.** A push of hundreds of commits is read in batches and passes when clean; one with a key in the middle is held at that file and line.
  - **A push is read against the remote it goes to.** What the other remotes of the repository have says nothing about this one, so a branch fetched from one remote and pushed to another is read, and a push over the 5000-commit limit says how to get through (push an earlier commit first, or fetch the remote first).
  - **A push to another address is read in full.** A repository that fetches from one address and pushes to another (a `pushurl`, or a rewritten push address) no longer has what it fetched counted as already sent. A remote whose name is `origin/fork` is not `origin`. A push of more than 768 MiB is asked to go in pieces, so that an approved one can be read again in time.
  - **More of a change is read.** Files git treats as binary, renamed and edited files, files that were symbolic links, the lines a conflict resolution adds, a commit's message and headers (a merged signed tag's text included), a tag's message and the names of files, whatever characters they hold, are all read. A key written after an escaped character such as `\u003d` is found. A line that happens to look like part of a diff no longer hides the lines after it. A pushed tag, file or folder that is not a commit is read too.
  - **A busy minute does not waste an approval.** When the box is busy checking other changes, the hook now waits for room, instead of failing after you approved. If it still fails, it says why.
  - **No second factor, no override.** A box with no passkey or key enrolled refuses a held change's override and says how to enrol one, because nobody else could approve it.
  - **Submodules are covered.** `ozbox guard install` now puts the hooks in submodules and linked worktrees too.
  - **A box whose secrets service is down still checks the shapes of keys when a commit is made,** and says that stored keys were not checked. A laptop with `ozbox` in `/usr/local/bin` is no longer taken for a box.
  - **Not yet run on a real box.**
</Update>

  ## Preview: a resize or an upgrade now says what will end, and saves your uncommitted work first

  A resize, and an upgrade that stops the machine, end every program on a box. Before it asks you to confirm, `ozbox` now lists what will end, and after you confirm it gets the box ready. **Sessions come back; running programs end.** The coming back has **not yet been run on a real box**, so do not rely on it yet.

  - **The plan says what ends:** the supervised runs, the coding-agent sessions (Claude Code reopens its conversation; other agents get their window back, not their conversation), and everything else running in the box. If the box cannot be asked, the plan says "could not list", never "nothing running".
  - **Runs are asked to end first.** Each is asked to end, given ten seconds, and stopped if it has not. The command reports each one: ended when asked, stopped, cancelled while queued, or already finished. New runs are refused for up to ten minutes, and the hold ends by itself.
  - **Uncommitted work is saved without touching anything of yours.** In each git repository under `/work` (up to four folders deep, including your home folder and repositories nested inside another), a hidden snapshot of everything uncommitted (new files that are not ignored too) is kept under `refs/ozbox/wip/`. Your files, index, branch, stash and remotes are not changed, nothing is pushed, and no hook of the repository runs. **To get a snapshot back without touching newer work,** in that repository run `mkdir ../recovered && git archive <ref> | tar -x -C ../recovered` (a copy in a separate folder), `git diff HEAD <ref>` to see what differs, or `git show <ref>:<file>` to print one file. Do not run `git restore --source=<ref> .` over a folder you kept working in: it replaces every file the snapshot holds and removes files it does not.
  - **If the box was not fully ready, you are asked again** before it is stopped, because `/work` is kept either way. Add `--strict-checkpoint` to `ozbox resize` or `ozbox upgrade` to refuse to stop the box unless it was fully ready (a program that ignores the request and is stopped after the wait does not count against it). The refusal says exactly what had already happened, and new runs are allowed again.
  - **Nothing is typed into your terminals.** Agent sessions come back from their records, not from anything sent to them.
  - **Nothing is pushed, also when the box stops or pauses itself.** The box's own stop, its idle stop and a cloud interruption notice save the same hidden snapshot and write no visible branch.   - **An older box** whose agent predates this is told so in the plan: its uncommitted work is **not** snapshotted and its runs are **not** asked to end, and you are asked again before it is stopped. `--legacy-checkpoint` uses that agent's own checkpoint instead, which writes a visible branch `wip/<box>/<time>` and **pushes it if the box has a push remote**.

<Update label="November 15, 2026" tags={["CLI", "Security"]} description="AWS secrets key">
  ## A box you already have can move its secrets store to your fleet's KMS key

  A box made before your fleet's KMS key existed kept its secrets store's key in a file on its system disk, so every upgrade would lose the store, and there was no way to give such a box the key. Now there is, and nothing is entered again.

  - **`ozbox adopt-fleet-key <box>` moves the store to your fleet's KMS key, in place.** The box's role is allowed to use the key for that box's own secrets, and the box re-wraps its own store while its secrets service keeps running, then swaps it in during a short stop. `--dry-run` shows what changes first.   - **The box's secrets service is down for a short time, and the time grows with the store.** Expect a few seconds plus about a second or two for each secret it unlocks when it starts (a store of 100 secrets can take a minute or two). `ozbox env run` and the dashboard's secret reads wait or retry meanwhile.
  - **Secrets read through the key service cost a little time after a pause.** Each secret the service has not unlocked in the last five minutes takes about a second to unlock again (an estimate, not yet measured on a real box); one that was used recently costs nothing extra.
  - **Nothing is destroyed until you commit.** The box keeps the key file on its system disk until this command has seen, as the box's root through AWS Systems Manager (your AWS sign-in needs the policy the fleet module outputs: it can run one fixed document of yours on your boxes, never a shell), that the store is on KMS, and written the label that makes upgrades keep it. The box user's own answer is never trusted for that. A key you escrowed in a vault before the move is not removed from it.
  - **`--cancel` takes the store back before it takes the grant away.** The box records the cancel itself and, if it had moved, re-wraps its store back under the file key, so nothing written in between is lost; only then are the mark and the grant removed. A box that cannot confirm keeps its grant.
  - **A move that is cut short puts itself right.** A reboot half way no longer leaves the secrets service refusing its store, the box's lock frees itself when a run dies, and a box that lost its tag and its grant to two operators acting at once is reported, never put back on its own: `--cancel` offers the copy made before the move only when the cloud's own tag list shows no label and the key service itself refuses the box, and asks you to type the box's name first (it says what that loses).
  - **A box with its metadata guard missing is refused before anything changes**, and a store that is written too often to be re-wrapped waits longer before each new try and says so.
  - **On AWS, an upgrade reads the store's key from the box's root, not from what the box says over SSH.** An unlabelled box is reported as lost, kept by escrow or unknown from that, and when the root channel cannot answer, the box's secrets service is not ready, or the box's program is older than the check, it is unknown and refused unless you accept a new store, never "kept". The box's firewall list can no longer be tightened to cut it off from its key service.
  - **A box that cannot move its own store is refused before anything changes.** A box made on an earlier release cannot (this includes boxes made on 0.1.1): upgrade it first, to an image built from a release that includes this command (the plan says what to enter again if its store would be lost, and that one time is the only time it loses it), then run the command. The upgrade plan now reminds you when your fleet's key is set and the box does not use it.
  - **`ozbox upgrade --use-fleet-key` on AWS now rests on what the box's root says.** Whether the store is empty and on a file key is read through Systems Manager, as for the other checks, and a box that cannot answer is refused. A box whose copy of the key is kept in this computer's keychain is reported as kept, as on the other clouds.

<Update label="November 15, 2026" tags={["Dashboard", "Security"]} description="Roles">
  ## Decide who may do what on a shared dashboard

  Everyone who could sign in could do everything, including watch a browser session and change the settings. Now each person has a role.

  - **Owner, member or viewer.** An owner can do everything. A member does the work: starts runs, approves what agents ask, watches and takes over a browser, and uses a box's terminal, files and IDE. A viewer can look at boxes, runs, costs and the audit log, and nothing more.

Add `role=viewer` to a `--person` to start someone as a viewer, or change a role later in Settings → Members & roles with your passkey. The change is recorded in the audit log, and a dashboard always keeps at least one owner.
  - **Pages match the role.** What a role may not change is shown read-only with a line saying why, and a button it may not use is not offered. The server refuses the same requests either way.
  - **On a box with no sign-in, more is refused.** Deleting what the bill found, granting access to production, changing the permission rules, applying a change that cannot be undone and changing how the dashboard is reached now need a sign-in with a passkey there, as taking over a browser already did. <Update label="November 15, 2026" tags={["CLI", "Security"]} description="Run a web app's tests on a box">
  ## A declared command can now run your real tests: tools, settings, a server and a browser

  Before, a command you declared on a box could not find your tools, could not be given a plain setting like a port, could not read your project folder, and an agent could edit the script it ran to read what the command received. Now one declaration covers a whole test run. See [Run a web app's tests on a box](/use-cases/secure-agent-workspace).

  - **Plain settings.** `vars` fixes a value for every run, and `pass` names values you may give with `--pass NAME=value`. They are never secrets: a value that looks like a key, or holds one you stored, is refused, and so is a name that decides how a program starts (`PATH`, `NODE_OPTIONS`).
  - **Rename a secret as it is delivered** (`{"name": "STORED", "as": "OTHER"}`), so you do not store a second copy.
  - **Pin a script by its content.** The box checks it every run and runs a read-only copy of exactly what you approved, so editing or swapping the script, even a moment after the check, no longer reaches the key. A changed file stops the run and says which. Pin a folder too (`pin_tree`, for a package), and a script that receives a secret is refused unless everything it imports is pinned; `ozbox env policy pin --entry FILE` lists it all.
  - **A server that stays up.** Mark a command `service` and use `--start`, `--stop` and `--status`. It listens only on this box's loopback, waits for its health check, and another command in the project can reach it. It receives no secrets.
  - **Tools and browsers on the command's PATH.** The tools your declaration names are copied read-only from the catalog's install. A project with a command that receives a secret must pin every tool by its digest, and a browser is copied only for the revision you approved; a command that receives a secret cannot drive a browser.
  - **A command that receives a secret runs as a user of its own.** A server, a browser or any other command can no longer read it from the system's process list. A box from before this refuses such a declaration and says to run `ozbox upgrade`.
  - **Before you have a second factor, no command can be given a secret.** The box cannot tell you from an agent, so it refuses any declaration that gives a command a secret and hands none out, until you enrol a passkey or make the box with `ozbox create` from a computer with a keychain. Declarations with no secrets are accepted, and a stored value cannot be replaced from the box.
  - **The command can read its own project folder, and nothing else of yours.** Before, runners were in the box user's group; they are not now, and a runner made earlier is taken out of it.
  - `ozbox env policy pin --dir DIR --commit SHA [--entry FILE] [--tree PATH] [--tool NAME=DIR] [--browser NAME --browser-cache DIR] [FILE...]` prints the digests to paste into a declaration. Run it on your own computer in a clean checkout at the commit the box reports: a digest taken on the box only freezes what an agent may already have changed. A box from before this release refuses such a declaration and tells you to upgrade.
  - **A command that receives a secret sees only what you approved of the project.** Its folder is a private, read-only view with just your pinned files and folders and your writable folders in it; a file an agent adds or changes cannot reach the key, and after the first run the box does not read the folder at all, so each run starts faster. Such a command runs exactly the words you approved, names the environments it may use, takes no host names or URLs from the caller, and needs exact egress hosts.
  - **Production values stay out.** A value stored as production anywhere on the box is production under every name, a file named for production is not imported under another environment, and you can list your own production identifiers per project.
  - (Tested with a simulated machine; a run on a real box is still to come.)
</Update>

<Update label="November 15, 2026" tags={["CLI", "Security"]} description="Secrets can hold any value">
  ## Secrets can now hold any value, including spaces, quotes, JSON and several lines

  A `.env` value with spaces (an address list), quotes, a JSON document or a whole private key used to be refused. Now it is stored and handed to your program exactly as you wrote it.

  - **`ozbox secrets import` stores any value.** A quoted value may run over several lines (a PEM key, a service-account JSON). The preview marks a value that is stored in its encoded form with `(stored encoded)`, and still shows names and fingerprints only, never a value. Only a blank value, a value with a NUL byte, one over 96 KB, or a quote that is never closed is skipped, with the reason. Every key is checked before any is stored; if the disk itself refuses part-way, run the import again to finish.
  - **`ozbox env run` gives the program the exact value,** and anything it prints that contains the value, or one line of a multi-line value, or the value written inside JSON, still has it removed.
  - **On a box, a value with a line break cannot add or replace another variable.** Values now reach the command directly, not through a file the service manager parses.
  - **A key that only fits in a command line when it is plain** (`{{secret:NAME}}`) says to read it from the environment instead, when it holds spaces, quotes or lines.
  - **A box made from an older image cannot take these values yet.** The import tells you which keys wait for `ozbox upgrade` and sends the rest. A store that holds one of these values cannot be opened by an older program, which says so rather than hand back the wrong text; `ozbox secrets status` shows how many are stored this way.
  - Existing keys are not changed.
</Update>

<Update label="November 15, 2026" tags={["CLI", "Security"]} description="Importing keys, the box's PATH, auto-pause and the AWS CLI">
  ## Importing a project's keys no longer stops at the first awkward line

  - **`ozbox secrets import` reads a `.env` file the way other tools do.** Quotes around a value are removed, `export KEY=...` works, and a trailing ` # comment` is ignored.
  - **A blank value, or one that cannot be stored, is skipped and listed instead of stopping the import.** The list names the key and the reason, never the value. Every key is checked before any is stored, so a skipped key never leaves the rest half imported.
  - **`ozbox secrets approve --dry-run` no longer makes a real approval code.** It says what it would do and contacts nothing.
  - **Keys and approval codes no longer go through the box user's shell.** `ozbox secrets import --box` and the approval calls used to run `ozbox` on the box through the box user's own shell, whose start-up files the box user (and so an agent working there) can edit, so a planted shell function could copy what was sent. They now go through the box's separate secrets account, sealed (see the entry on the secrets route). This does not protect against root on the box, and boxes whose secrets service is not running cannot take keys.
  - **The box user's own `~/.local/bin` and `~/.cargo/bin` now come after the system folders** in the PATH file that login shells read. This is tidiness, not a lock: the stock `~/.profile` still puts `~/.local/bin` first, and the box user can change its own start-up files.   - **`--dry-run` now stops every `ozbox secrets` command that changes something** (`import` even with `--yes`, the rotations, `put`, `remove`, enrolling or revoking an approval key), and `ozbox env run` and `ozbox env policy` refuse the flag instead of ignoring it.
  - **A connection that fails with the AWS CLI at version 1 now says so, and which `aws` it used.** Before, `ozbox init` blamed an expired sign-in, or a connection just failed without a word. Version 1 can open a connection to a box; only `aws sso login` needs version 2. So `ozbox connect --ssh --write` no longer refuses a computer whose first `aws` is version 1, and a connection that works costs no extra check.

<Update label="November 15, 2026" tags={["CLI", "Security"]} description="Secrets route">
  ## Keys and approvals now reach a box through a route the box's own user is not on

  Before, `ozbox secrets import --box`, signing an approval and enrolling a key went through the box user's own SSH account, where an agent's shell startup files could read what was sent. They now go through a separate account that only runs one command, and every request is sealed so that anything on the way sees only ciphertext.

  - **`ozbox secrets import --box`, `ozbox env policy set --box`, `ozbox secrets approval-key` and `ozbox secrets approve` use the new route.** The first request to a box pins that box's key on your computer and prints its fingerprint; a box whose key later differs is refused and nothing readable is sent. `ozbox secrets ingress pin --box <name>` shows or checks the pin, and `--replace` accepts a new key on purpose.
  - **A box made before this release is refused with a sentence that says what to do**, and the old route is not used instead. `ozbox upgrade <name>` gives the box the new account and keeps `/work`: on AWS the machine is rebuilt from the newer image, and on Hetzner the server is replaced (the box needs a newer image than the one it runs). The one-time cost, when the box keeps its secrets store's key in a file, is a new, empty store, because that key cannot be copied off the box without the account; the upgrade lists what to enter again and asks for `--accept-new-secrets-store`.
  - **The dashboard's first-time setup code is no longer in the box's logs.** Read it on your own computer with `ozbox secrets ingress setup-code --box <name>`.
  - **A box that keeps its store's key in a file can now keep a copy in your computer's keychain.** Run `ozbox secrets ingress escrow --box <name>` once; `ozbox upgrade` then keeps the box's secrets across the upgrade and puts the key back for you, where before it asked you to accept a new store.
  - **A box's AWS role can no longer read every Parameter Store value in your account.** Boxes now carry only small policies made for them once per account (`ozbox-box-session-manager` and, when used, ones for the box's own parameters, the fleet key and session logs), never an inline policy and never AWS's broader Session Manager policy. `ozbox init` makes them; an upgrade that needs a permission your daily role cannot grant is refused before the box is stopped. `ozbox upgrade --use-fleet-key` moves a box with an empty store onto the fleet key; boxes you already have switch at `ozbox upgrade`, and the steps for an existing account are in the infra README.
  - **The key import route is fixed and stricter.** The ingress account's settings now pass sshd's own check, and a setup that fails leaves the account unable to log in. It has its own SSH key, no agent is forwarded, `ozbox upgrade` gives an existing AWS box the account, and the store-key copy and the first-time code need an approval from your approval key once the box has one.
  - **`ozbox init` now sets up the fleet's secrets key on AWS.** It is shown in the plan with its alias, created only when you approve, and recorded in your config, so new boxes keep their secrets store's key in KMS and an upgrade keeps the store. Setup runs as the identity that has the `OzBoxKeyAdmin` permissions; your daily operator role is not given any right to the key. If setup cannot create keys, it says what to ask an administrator for and your boxes keep a file key. On Hetzner a box uses its TPM, or a file key you escrow to OpenBao or your keychain.
  - **`ozbox init --issuer-package <zip> --issuer-package-sha256 <hash>` also plans the off-box issuer for Production secrets** in your account, from a package you built. Nothing is created without your approval.

  ## A box's secrets stay out of an agent's reach from the first minute

  A security review found ways for an agent on a fresh box to give itself the power to approve changes, and for a backup to carry the key that opens the box's secrets. Those are closed.

  - **Your computer's key is a new box's first approver.** `ozbox create` pins the key kept in this computer's keychain on the box, so nothing on the box can enrol a key of its own. A box made without one waits for a passkey in its dashboard.
  - **Backups, snapshots and clones no longer hold a box's store key.** A box without a cloud key service keeps its key in its own vault when it has one (box secrets on OpenBao), so an upgrade still keeps its secrets; without a vault an upgrade starts a new store, and `ozbox secrets status` says so.
  - **A run's model token reaches the model only.** The broker passes on a model's answers and its model list, and refuses everything else your cloud account could do (training jobs, files, fine-tuning). A run with a spend limit stops if its provider answers in a form that cannot be counted.
  - **An approval for a box's vault settings covers that exact address**, and a new address needs a new token. `ozbox box-secrets` shows the address and what to approve.
</Update>

<Update label="November 11, 2026" tags={["CLI", "Platform"]} description="Versioning">
  ## One version for the program, the daemon and the image

  The `ozbox` program, the box daemon and the machine image now share one version, such as `0.3.0`. Before 1.0 a minor version may break anything and a patch never does, so the program refuses to upgrade a box to an image from a different minor version and tells you which side to upgrade. Releases are tagged `vX.Y.Z` (the program) and `image-vX.Y.Z` (the image). See [Releasing](/releasing).
</Update>
