**Decision.** An agent that needs a real web page (a portal, a form, an application with no API) gets a browser as part of the
tool host (ADR 0026): `browser_open`, `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_extract`
and ten more. The browser is a **Chromium on the box**, started by a small worker process that answers only the tool host that started it
(on a box with the dashboard on it the worker has a Unix user of its own, amendment 4; the earlier amendments say what the
shared-user limit meant before that, and what it still means for a dashboard on another computer). People
keep Firefox on the desktop (ADR 0012); the agent's Chromium is separate, headless, and has an isolated profile.

1. **One door, no raw debugging port.** Chromium starts with `--remote-debugging-pipe`: the DevTools protocol travels over a pipe
   the worker owns, so no port listens and nothing on the box (including an agent's own shell) can attach to it by address. The
   worker is `ozbox browser-worker`, a run on the box with its standard input kept open (ADR 0019): a request is one sealed
   line in, the reply is one sealed line in the run's log (amendment, part 1). Nothing new listens. A library such as browser-use may be an agent engine only
   if it acts through these tools; it is never handed a debugging address, because there is none.
2. **Every action is a tool call the permission engine decides** (ADR 0022, 0026): the tool, its group (`browser`), read or
   write, and the *domain* as the path, so a rule can say "never on this site". The audit chain gets the action word and the
   field *name* (`browser type password`), never a typed value, an address, a page or a result. Ordinary in-page actions are
   governed by the engine's rules and plan-only mode but do not ask by default (a click is not a decision); the risky ones below do.
3. **Risk is judged by the worker, twice.** A call first asks the worker to *preview* the action (what is it, how risky), the
   engine then decides, and the worker re-judges when it *acts*, so an approval covers the risk that was shown, not whatever
   the page turned into: the approval is bound to a fingerprint of the element, the form's destination and the page, and is
   refused if any of them changed (amendment, part 2). Four things ask a person first, with the page, the fields and their values shown (a password, a card
   field or a field marked secret as `[masked]`): **submitting a form or any non-GET request** on a site not marked safe; **sending
   or posting** (a send or post button, and the compose screens of well-known mail and chat apps); **opening a downloaded
   program or script**; and **a site that is not on the project's allow-list** (the box's own loopback is always allowed).
   **A purchase or payment is refused for the agent** by default (a checkout page, card fields, a pay button); the owner can
   change that to approval every time. A site marked safe skips only the form-submit question for a form that goes back to
   that same site, never sending, paying, or a form that goes elsewhere. One approval covers one call. Sending and payment are
   recognised by heuristics (words, paths, field names): see the amendment, part 4, for what that misses.
3. **A CAPTCHA or bot check is never solved.** The worker recognises the common ones (challenge frames, widget markers, "verify
   you are human") on any action; the session goes to *taken over*, the agent is told to stop, and every channel is notified.
   There are no solvers and no fingerprint spoofing, and the browser says what it is: its own user-agent plus `OzboxAgent/<version>`.
4. **Take over, hand back.** A person can take the session at any time from the dashboard; while they hold it the worker refuses
   every agent action (the tool says a person holds the browser), and a person's pointer and key input is relayed into the same
   session, so it is audited the same way. **Hand back** is refused while a challenge is still showing. A person's typing is
   counted, never recorded.
5. **Live view is a stream of pictures the worker takes, not a second desktop.** The dashboard asks for the page as a small
   JPEG a few times a second and sends clicks and keys back through the same session. We chose this over showing the box's
   KasmVNC desktop because the agent's browser is headless (no display to show), it lets the worker blur secret fields in
   what is kept, it works the same from a phone, and the person's input goes through the one audited door. The desktop remains
   for people. The cost is a lower frame rate than a real desktop and one run per frame on the box.
6. **Recording and replay.** Each session keeps, on the box under `/work/.ozbox/browser/sessions/<id>/`, a list of steps (action
   word, host and path without the query, field names, risk, who acted, how it ended) and a screenshot per step with secret
   fields blurred first. A step never holds a typed value or page text. Recordings are kept **30 days** by default (a setting
   per project) and pruned when a session opens, so no timer runs on the box. The replay page is the step list with its pictures.
7. **What the model sees.** A snapshot is the page's text and structure with numbered elements. A password, a field marked
   secret and anything that looks like a card number, a dashed national ID or a labelled ID number is masked in one place, so a
   snapshot, a result and a recording cannot disagree about what was hidden. A screenshot is used only when layout needs it. A
   project can list sites a *local* model alone may read; a hosted model's run is refused those pages.
8. **Site manners.** robots.txt is honoured for automated navigation, requests to one site are spaced, and the identity is
   honest. The box's own loopback and sites the owner exempts are not held to it.
9. **Limits that stop cleanly.** A browsing task has a time limit and an action limit (30 minutes, 200 actions by default), warns
   at 80 %, and at the limit **pauses between actions**: the worker saves where it was and closes the browser, so nothing is
   left half-submitted; a person resumes it from the dashboard. Waiting for a person (an approval, a challenge, a take-over)
   pauses the same way after 30 minutes. A box runs a limited number of sessions at once (three by default), each with its own
   profile and a bounded amount of memory.
10. **Results and files.** `browser_extract` reads data into a JSON schema (`x-selector` says where each value is) and validates
    it; a page that does not fit is an error, never a guess. Downloads land in a held-back folder; documents (PDF, images,
    spreadsheets, text, archives) within the size limit move to the session's downloads folder, and scripts, installers and
     anything that starts like a program are held and need an approval to be opened. Profiles and held-back files are not reachable
    through the files tools. An upload comes only from upload folders the person names, always with an approval (amendment,
    part 3).
11. **Network.** The box's own connection by default; a project can bring its own proxy. Oz Box ships no proxy service.

**Why.** A browser is the biggest hole you can give an agent: it can log in, buy and post. The answer is not to forbid it but to
make every step a decision someone can see, keep the dangerous steps for a person, and keep a record good enough to replay
without becoming a copy of the person's data. A pipe instead of a port, a worker that judges risk itself, and a take-over that
the tool refuses to bypass keep the controls in one place.

**Consequences and what is not covered.**
- **Same-user limit.** As in ADR 0022, the worker and an agent's shell ran as the same Unix user. The first amendment closed
  the doors that do not depend on that (the daemon's run routes, forged lines, forged approvals, the cleartext log); what
  depended on it is listed in its part 6. Amendment 4 gives the worker a Unix user of its own on a box with the dashboard on
  it, which closes that list there. A worker started through the box daemon (a dashboard on another computer) still shares the
  box user with an agent's shell, and the tools are then the supervised path, not a sandbox against a hostile agent with a
  shell.
- **Logins by vault autofill are not built yet.** They wait for the Production secrets service (ADR 0029): until then the agent
  cannot sign in by itself, a person takes over to sign in, and the session's profile keeps the cookies (stored in the box's
  work disk, unreachable by the files tools, not yet encrypted separately).
- **Shared profiles and their allocation** are designed (a profile belongs to a person; sharing is by allocation) but only the
  name of the profile in the settings exists now; enforcement plugs into the secrets allocation when it lands.
- **Frames are polled**, a few per second, one run per request on a real box. Smooth video is not a goal.
- **A running session does not survive the dashboard server restarting**; its worker stops at its time limit.
- **Frames and iframes**: the snapshot names a cross-origin frame but does not read inside it; what a frame loads or sends
  is judged like the page's own requests (amendment, part 4).
- **Downloads are checked by name, size, first bytes and (for an office document) the names of its parts**, not by an
  antivirus engine. "Document" means "not flagged", not "safe"; archives are held back.
- **No claim of this being proven on a real box** until the real-box check has been run; CI runs a real Chromium on a local test
  site, not a cloud box.

## Amendment (2026-11-11): one authenticated door, judged at the destination

A security review (2026-11-10) found that the seam between "the engine decided" and "a person approved" was one boolean on
the worker's request, that the daemon's routes for the worker's input and log answered any process on the box, and that most
checks judged only the agent's own top-level action. This amendment records what changed and what is still open.

**1. One authenticated control path.**
- The tool host makes a 32-byte key for each session and hands it to the worker on the first line of its standard input (the
  only line in the clear; never an argument, the environment or a log). Every later line, both ways, is sealed with
  ChaCha20-Poly1305 under a key derived per direction, bound to the session id and numbered. A line that does not open, or that
  repeats or goes back in the numbering, is refused, and the refusal is a step in the recording. The worker refuses to start
  without a key. So writing into the worker's input (through the daemon or `/proc`) does not drive it, and a bare
  `ozbox browser-worker` drives only a Chromium of its own.
- The worker's run is a *controlled run* (ADR 0019 amended in code): the daemon gives the starter a capability once, keeps
  only its SHA-256, and answers the run's `stdin`, `log` and stop only to a request that shows it (`X-Ozbox-Run-Capability`
  header, compared in constant time). The control side keeps it in memory. An older daemon that does not give one is not used.
- Replies are sealed too, so the run's log on the box holds no frame, snapshot, extracted value or page text in the clear.
- Taking over, handing back and a person's input exist only on the dashboard's routes. Taking over and resuming need a second
  factor shown a moment ago; input and hand-back are accepted only from the person who took over. *(There were no
  roles: anyone signed in could watch. ADR 0039 adds them: a viewer cannot watch, a member may watch and take over, and only an
  owner changes the browser's settings.)*

**2. A person's approval is a grant, not a boolean.**
- A risky call is marked so that the tool gate always asks a person, whatever an allow rule, a grant or the mode says (a deny
  still wins; the decision is recorded as `person_required`). The engine allowing a call is never an approval.
- Only an approval request a person decided yields a grant: a MAC under a key of its own over the request id, the exact
  action, the risk shown and a fingerprint of what the action was aimed at (the element's tag, type, label, name and link, the
  form's destination and method and its field names, and the page). The worker judges again before it acts, refuses a grant
  whose fingerprint or risk no longer matches ("the page changed"), and uses each one once. The approval text shows the
  destination and a short check of the fingerprint, so a page that changes where a form goes makes a different request.
- The recording names the approval request a step ran with.

**3. Uploads are an allow-list.** A file is uploaded only from the folders the person names in the settings (default
`/work/uploads`) or the session's own downloads, after every link in the path is resolved; never from the home folder, never
a dotfile or dotfolder, never a key or certificate file. Every upload asks a person and shows the file by its place.

**4. Judged at the destination.** Every request the browser makes (a tab, a popup, a frame from another site in its own
process, a worker) and every hop of a redirect is paused and judged before it goes out:
- a document (page, frame, popup, redirect) loads only from the box itself, the allow-list, a site a person approved for the
  session, or the destination of the action a person just approved;
- anything that is not a GET goes out only to a destination a person approved for the action now running, or back to the
  page's own site when that site is marked safe. The page's site is the one the browser committed, never a request header, so
  a page with no referrer is judged the same. A post that is held is remembered for that element, and the next attempt asks;
- a `data:`, `blob:` or other non-web address is never loaded as a document, and nothing is sent to one; the agent does not
  act on a tab showing such a page;
- an address inside the box's network that is not the box itself (private, link-local, shared, the metadata address, in any
  spelling of IPv4 or IPv6) is refused; host names are normalised (case, trailing dot) and a name that is not ASCII must be
  written in its `xn--` form;
- robots.txt is honoured on every page load, including a redirect or a link a page follows; a site whose robots.txt was not
  read yet is held once, read, and the agent tries again. The pause between loads applies to the agent's own navigations,
  links, back, forward and reload, not to loads a page starts by itself;
- a popup is not switched to for the agent: it is reported, and a switch is judged;
- a dialog is dismissed for the agent; while a person holds the session it waits for them in the live view.

Sending and payment detection stays a heuristic (button words, page paths, card and autocomplete fields, a few known mail and
chat apps). A send or a payment labelled in another language, or behind a script, may present only as a generic submit. The
safe floor is that a form or post to another site, or from a page not on a safe site, always asks.

**5. Smaller changes.** Archives are held back; an office document with a macro or a program inside is held back; an approved
held-back file is released into the downloads folder as a recorded step, and its held-back path is never handed out. Each
session's run has a memory cap that the box also admits it by (default 1536 MiB, settable). Profiles, downloads and
recordings are folders only the box user can open (0700). Masking stays a pattern match (a card number by its checksum, a
national ID by a dashed number or an English label), so an unusual format can show. A settings change is recorded by which fields changed and whether
the change makes browsing less careful; the settings file is the server's own (0600). Recordings are pruned when a session
opens or closes.

**6. What waits for a Unix user per run.** *(Amendment 4 below closes this list for a worker started by a dashboard that runs
on the box. It stays true, as written, for a worker started through the box daemon.)* The worker, its Chromium and its
profiles still run as the box user, so a process that runs as that user can:
- read the session key from the worker's memory, or race the worker for its first line, where the kernel allows it;
- read a profile's cookies from disk (Chromium's basic password store does not encrypt them);
- start its own Chromium, or a worker, against a profile directory;
- open Chromium's control pipe through `/proc/<pid>/fd` and drive the browser with no session key at all: the kernel's
  ptrace restriction (Yama) limits attaching, not reading a process's open files as the same user, and Chromium is dumpable
  again after it starts whatever the worker sets for itself, so marking the worker non-dumpable would not close this (a
  security review, 2026-11-11, named it; it is the strongest item here);
- stop or kill the worker (a denial of service).
The fix is to run the worker, Chromium and the profiles as a separate Unix user (or in a user namespace) that the agent's
user cannot read or signal, with the profile folders 0700 to it. That is the right architecture and it is planned with the
per-run users; until then, a box that holds a person's live sign-ins in a browser profile should not also run an agent with a
shell.

## Amendment 2 (2026-11-11): what a dashboard with no sign-in may do on a box, and a worker that cannot be reached by forgetting

A security review (2026-11-11) found two things:

- **Step-up without a sign-in.** A dashboard with no sign-in treated every request as one from a person who had just shown a
  passkey, which is true of the person's own computer (the access token is in the address it printed for them) and not of a
  box, where another process may hold that token. On a box, a dashboard with no sign-in now refuses taking over a browser,
  resuming one and changing the browser's settings, and says why (`sign_in_required`); on the person's own computer nothing
  changes. One function decides it (`step_up_gate`). *(ADR 0039 moved the dashboard's other routes that ask for a fresh second
  factor, deleting what the bill found, permissions and applying a plan that cannot be undone, to the same function.)*
- **A capability only in memory.** A controlled run's capability lived only in the box daemon's memory, and a run the daemon
  had no capability for was treated as an ordinary run. A run carrying the browser worker's label is now reached only with
  its capability, so one whose capability the daemon no longer knows (it started again while the run went on) is refused, not
  opened. The worker's runs end with the daemon's today, so this was latent; it now fails closed.

Part 6's list gains the item it was missing (a process of the box user can drive Chromium through its control pipe). The fix
for all of part 6 is a Unix user of the browser's own, which amendment 4 builds; the browser stays Preview until it has run on a
real box.

## Amendment 3 (2026-11-11): what a slower Linux machine showed

On Ubuntu with Google Chrome (the image's browser), two of the hostile-page checks failed where they pass on a fast
laptop. A trace of every message between the worker and Chrome found four causes. None was a way past a guard: each one
held back what it should have let go, or hung. Three were the worker's and are fixed; the fourth is Chrome's.

- **A tab is driven only once it is set up, and nothing runs before its setup is done.** The worker attaches to every tab,
  frame and worker paused and sets it up (requests judged, the page's events on). The setup commands were sent without
  waiting for their answers, and the tab already open when the worker starts is not paused. On a loaded machine the
  agent's first navigation could commit before the page's events were on, so the site the tab committed was never learnt:
  a safe site's post to itself, and a post a person had approved, were held. Now a paused target is let run only once the
  browser has done every setup command, and never when it refused one (it stays paused, so it sends nothing); the worker
  drives a tab only once its setup is done, and refuses a tab that holds a frame or worker that could not be set up.
- **A page that finishes is noticed however it finishes.** Waiting for a page after an action could miss its load event
  when the event arrived between two waits, and a jump within the page or a page restored from the back-forward cache fires
  none. Either cost a full 20 seconds. The wait now looks at every event it takes, and the main frame stopping counts too.
  It also saw a navigation only once it started loading, so a form post that a person approved could start after the
  action was judged finished, when its approval had already lapsed, and be held. A navigation now counts from the moment
  the page asks for it.
- **A wait keeps answering the browser.** A timed wait used to sleep, so a request the page made meanwhile waited paused
  until the next action. It now answers them as they come.
- **A crashed tab is reported, not waited on.** Google Chrome on Linux (156, and 157.0.8103.50, the stable release when
  this was written) stops a tab's renderer when a page calls `window.open` from a click: a check in Chrome's own event
  timing code fails (`window_performance.cc`, "info.processing_start_time >= render_start_time"). It happens whether or
  not the worker holds the new window paused, without the worker's device metrics on it, with the refused window closed,
  with Chrome's backgrounding of hidden windows switched off, and with no window made at all (below); macOS does not do it.
  Until now every later call on the dead tab waited 30 seconds for an answer that could not come. The worker now notices
  the crash, answers at once that the page in the tab crashed, and the tab works again once the agent opens a page in it.
  The crash itself is Chrome's and is a known issue: on a box, a page that opens a window from a click ends the agent's
  tab. CI tests with the current stable Chrome, the package an image is built with, rather than an older copy on the
  runner image; its popup check asserts what the worker controls (the window is refused and reported, the crash is
  reported at once, a new page brings the tab back) and says why.

Two changes of behaviour came with this:

- **A page cannot open a window.** Chrome starts with `--block-new-web-contents`, so it refuses a window before anything is
  made. Part 4's "a popup is not switched to for the agent: it is reported" becomes: a window a page tries to open is
  reported, where it would have gone and why (judged like a page load there: `new_domain`, `robots`, `internal`, or
  `new_window` when the address itself would be allowed). The agent opens that address itself if it needs it, and that is
  judged like any navigation. A page that needs a window (some sign-in flows) has to be handled by a person taking over.
- **A refused page load leaves the tab where it was.** A load refused for the tab itself is stopped (aborted) rather than
  failed as blocked, so the tab keeps showing its page instead of Chrome's "blocked" error page. A refused frame still shows
  as blocked inside its page.

Pictures of a tab (the recording's, the live view's) bring the tab to the front first.

## Amendment 4 (2026-11-11): the browser has a Unix user of its own

Part 6 of the first amendment listed what a process of the box user (an agent's shell) could still do to a browsing session:
read a profile's cookies, start its own Chromium or worker against a profile, open Chromium's control pipe through
`/proc/<pid>/fd`, read the session key from the worker, and stop the worker. Each of those depends on the worker and the agent
being the same Unix user, so the fix is architectural: the worker, its Chromium and its profiles run as **`ozbox-browser`**.

**The user.** A system account with no login and a locked password, its own group, **no supplementary group** (it is not in
the box group, so it cannot open the box daemon's socket, and it is not the box user), and a fixed id (1501), because its
folders are on `/work`, which outlives the system disk: an upgrade replaces the system disk, and the id has to be the same on
the next one. The image creates it. First-boot configuration runs `ozbox browser-setup` (the script is carried in the program,
not in the first-boot text, which on Hetzner is nearly at its 32 KB limit), which makes the user when the image did not (a
machine built from stock Ubuntu), makes the folders below, and follows the user's id if a re-made system disk gave it another
one. The box's re-own script never treats this account's files as an old box user's.

**The launcher.** The box user cannot become another user, and the box daemon runs as the box user, so a root launcher does it
the way the per-project runner users are started (ADR 0018, item 8): `ozbox-browser.socket` listens on
`/run/ozbox-browser/launch.sock`, one `ozbox browser-launch` process per connection, as root. It reads the session's first
line, refuses anything that is not what the browser tools send (the recording, private and work folders must be this box's
fixed ones, the policy must validate, the memory and time limits must be present and bounded), and starts `ozbox browser-worker`
with `systemd-run --pipe` as `ozbox-browser`. **The connection is the worker's standard input and output**, so the sealed
channel (part 1 of the first amendment) is still the only way in: nothing new listens on the network, there is no second
protocol, and the launcher never sees a plaintext request or reply after the first line. A refusal is answered sealed with the
session's own key, so the tool host can say why.

**The socket belongs to the dashboard's user, not the box group.** If the box user could connect, it could start a worker as
`ozbox-browser` against any profile and drive it with a key of its own, which closes nothing. The socket and its folder are
root-owned and open to `ozbox-supervisor` only (ADR 0023). So the isolated browser exists **where the dashboard runs on the box
as its own user**. A dashboard on another computer reaches a worker through the box daemon, as the box user, exactly as before:
that path is not isolated and part 6 still describes it. The dashboard chooses by itself: it uses the launcher for the box it is
running on when the socket exists, and the daemon for every other box. Where the dashboard has not been given its own user yet,
the launcher is installed but not started, and starts when the dashboard is installed.

**The sandbox.** The worker's `systemd-run` call is a pure function with a test: its own user and group; `ProtectSystem=strict`
with one writable folder, its own tree; `ProtectHome`, and the box user's home, the other service accounts' folders and the
box's own sockets (`/run/ozbox-secrets`, `/run/ozboxd`, `/etc/ozbox`) out of its view; `ProtectProc=invisible`; `PrivateTmp`;
`UMask=0027`; a memory cap and no swap (the session's memory limit, which the box enforced through the daemon's run before),
a task cap and a run-time backstop; no core dumps; and the cloud metadata addresses refused by the kernel, so a renderer that is
taken over still cannot reach the account's credentials (the box's loopback stays open, which is how a person browses their own
development server). **Left out on purpose:** `NoNewPrivileges`, `RestrictNamespaces` and a system-call filter. Chromium's own
sandbox is made from user namespaces and, on Ubuntu, the AppArmor profile that allows it attaches at exec; a filter written
without a real box to try it on would either break the browser or give a false sense of safety. They are the first things to
try on the real box.

**The folders.** Everything is under `/work/ozbox-browser`:
- `private/` (0700, the browser's user and group): the profiles, a clean session's temporary profile, the downloads that were
  held back, a paused session's saved place (it holds the addresses of the tabs, which can carry a token) and the browser's home.
  Nobody else can open it.
- `shared/` (0750, group `ozbox`, setgid): the recordings (steps and pictures with secret fields already blurred) and the
  documents a session released. The browser's user writes, the box's group reads (the agent opens a document it was given), and
  the dashboard's own user reads through a POSIX ACL entry of its own (`u:ozbox-supervisor:rX`, access and default, set by the
  browser's user), because on a box with the scoped dashboard socket (ADR 0040, decision 3) it is not in the box group: the
  dashboard shows the replay. A released document is made readable by the group (0640); a held-back file never is.
- Uploads still come only from the folders the person names (default `/work/uploads`, part 3 of the first amendment), with every
  link in the path resolved. The worker is no longer the box user, so setup makes `/work/uploads` readable by others when it makes
  the folder; a file the box user keeps unreadable cannot be uploaded, and the tool says so.
- Profiles made before this release are in `/work/.ozbox/browser/profiles`, where the box user can read them. Setup, as root,
  **moves them** into the browser's private folder (as copies, so a link the box user made to one of them leads nowhere; the same
  Chromium reads them there, so sign-ins carry over), makes them 0700 to the browser's user and removes the old copy. A profile that
  is already in the private folder is not overwritten and its old copy is removed all the same; a link in the old folder is removed,
  never followed. Run again, it has nothing left to move.
- Root never follows a link the browser's user can plant. `/work/ozbox-browser` is root's (0751): the browser's user can enter it
  but cannot rename `private` or `shared`, setup refuses a link where either should be, and everything deeper is made by the
  browser's user itself, not by root.
- The launcher's folder `/run/ozbox-browser` is made the dashboard's when setup runs (the tmpfiles entry is applied then, not at
  the next boot). Once a box has been set up for the launcher, **its sessions never fall back to the box user's browser**: where the
  launcher does not answer, the start is refused with a message that says so, checked at every start. A session's recording says
  whether it ran as the browser's own user (`isolated`).
- Memory: every session is in one systemd slice (`ozbox-browser.slice`) with a ceiling of 60% of the box's memory and no swap, and
  the launcher refuses a session, sealed, when the memory it asks for is not free (`MemAvailable`). The count of sessions is still
  the dashboard's limit.
- A worker that ends by itself ends the launcher, and the dashboard sees the end at once; a worker that does not end after the host
  closed its connection is stopped by the launcher after five seconds.
- An upload is never taken from the browser's private folder, however a link reaches it, and an upload folder that has been
  replaced by a link is not an upload folder; the setting cannot name `ozbox-browser` or `ozbox-supervisor`.

**What this closes, on a box with the dashboard on it.** The agent's shell can no longer read a profile's cookies (the folder is
0700 to another user), start a Chromium or a worker against a profile (it cannot become the browser's user, and the only door that
does is the dashboard's), open Chromium's control pipe through `/proc/<pid>/fd` (the kernel refuses reading another user's open
files: the same refusal as for ptrace), or signal the worker. The session key no longer passes through a process of the box
user: it goes from the dashboard to the launcher's socket and on to the worker, with the daemon and the box user out of the path,
which closes the race for the first line.

**What it does not close.**
- A dashboard on another computer: the worker is the box user's, as part 6 says.
- The box user can still read recordings and released documents. That is the design: they are what the dashboard and the agent
  are for. The recordings hold no typed value, no page text and no address with a query, and the pictures have secret fields
  blurred, but a person's own page may show what they would not want an agent to see.
- The box user can still make a session stop: it can ask the tool host to close it, which is the tool. It cannot kill the worker.
- A person or a process with root, or running as the dashboard's user, is trusted as before.
- The sandbox is as strict as a Chromium that runs on an unknown Linux box allows; the omissions above are deliberate and named.
- Follow-ups from the 2026-11-11 review, not done here: `OZBOX_CHROMIUM` is not forwarded to the worker and `PATH` leaves out
  `/snap/bin` (a snap Chromium under a system user is unlikely to start; set the browser through `/etc/ozbox/browser.env`, to be
  added); `/work` is hidden from the worker by a deny-list, where an allow-list (`TemporaryFileSystem=/work:ro` plus binds) would
  be tighter; the dashboard follows links in `shared/` when it reads a recording (open with `O_NOFOLLOW` and check the owner); one
  lock covers all of the dashboard's launcher connections (a lock per connection); `/work/uploads` is world-readable (a group ACL
  for the browser's user would scope it); the `BufReader` that holds the first line is dropped, not zeroized; and the patch
  `fix/module-version` also changes the Hetzner provider and its reprovision probe was designed around the rebuild, so its merge
  order needs a look.
- Nothing here has run on a real box.

**What is tested, and what only a real box can show.** The decisions are pure functions with tests on any computer: what the
launcher accepts and refuses, the exact `systemd-run` arguments (no key among them, one writable folder, the hidden paths, the
memory and time limits), the launcher's connection handling with a stand-in for `systemd-run` (the first line and what follows
reach the worker, a refusal is sealed and starts nothing, a launcher that cannot start the worker says so), the dashboard's end
against a real socket (this box through the socket, every other box through the daemon, a launcher that goes away ends the
session), the worker's folder layout (profiles, held-back files and the saved place in the private root; recordings and released
documents readable by the group), and the setup script run against stand-ins for the account and service commands (the user,
its id, its folders and modes, the socket's group, nothing started until the dashboard has its own user, a second run changes
nothing). The real-browser suite runs with the private root set. **Only a Linux box shows:** that `ozbox-browser` really cannot
read `/work/ozbox-browser/private` from the box user, that `/proc/<worker>/fd` is refused to the box user, that Chromium starts and
its sandbox works under these unit properties (including `/dev/shm`), that the metadata address is refused for it, that the socket
refuses the box user, and that a released document and a recording are readable by the dashboard. Those are the real-box checks.
