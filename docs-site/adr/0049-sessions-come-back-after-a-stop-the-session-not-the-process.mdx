**Status.** Slice 1 is built and covered by local tests only (CI was unavailable). **Not yet proven on a real box:** nothing here has
run on a real machine, with a real tmux server, a real Claude Code, or a real resize. The first review (2026-11-13) found fifteen
things to fix, and a second check five more (a shutdown guard that failed open, an unattended settings rewrite, a nested `claude`
that evicted the real record, a sweep race, thin off switches); this text is the corrected design, and the proof script was rebuilt
so it cannot pass on a failed resume. The status
stays Preview until `scripts/real-resume-proof.sh` has passed on a real box.

**Decision.** A resize, an upgrade, a crash, an out-of-memory kill, a pause or a forced stop all end every process on the box:
RAM is lost, and hibernating would write secrets to disk (ADR 0045). So "survive" means the **session** comes back. A resize stays an
in-place apply (ADR 0036): quiesce, stop, resize, start, resume.

1. **A session record on `/work`, written continuously, and removed when it should be.** Each coding agent's hook writes one small
   file per agent session in `~/.local/state/ozbox/sessions` (the box user's home is on `/work`). It holds the engine, the engine's
   session id, the folder the session started in (which must be under `/work`), the tmux session and window, a place that identifies
   the tmux server and **pane** (two agents in split panes of one window keep two records), and the last-seen time. It never holds
   prompt text, a transcript path, an environment or a secret: only the session id and the folder are read from the engine's
   payload. A write is a flushed temporary file renamed over the record, mode 0600 in a 0700 folder; an unchanged record is touched
   at most every 30 seconds. The record is written on every event, not at quiesce, so a crash or a forced stop loses nothing. A
   corrupt, oversized, linked or mismatched record is skipped with a message; the others load. Records are opened without following
   a link and without blocking on a pipe, and every field is checked on read (names, place, folder, id), not just the ones a path
   needs. The records folder is never taken from the environment, and a folder that is a link or someone else's is refused.
   **Only the agent that owns a pane is recorded.** A `claude` started inside an agent's pane (`claude -p` from the agent's Bash
   tool or a script) inherits `TMUX_PANE` and reads the same settings, so it would replace the pane's record with a one-shot
   session. The hook therefore walks the parents of its Claude Code up to the pane's own process (`#{pane_pid}`) and records only
   when there is one Claude Code between them, not another one separated by a shell, and it was not started in print mode (`-p`,
   `--print`). A wrapper script and the program it starts count as one. Where the process table cannot be read, the old behaviour
   (record) is kept. **A record goes away five ways, and never because of a shutdown:**
   - the person ended the session: Claude Code's `SessionEnd` with the reason `prompt_input_exit`, `clear` or `logout` removes it.
     Any other reason (a shutdown's hang-up arrives as `other`) leaves it;
   - the window or pane was closed while the box runs (`tmux kill-window`): the daemon checks once a minute, and each new session
     checks once, and removes the record of a pane that is gone from the server that is running;
   - the tmux server itself ended while the box kept running (`kill-server`, an out-of-memory kill of the server): the record names
     its server's process, and it is removed only on **positive evidence about that process**: it is gone from `/proc` (or the number
     is now another program, not tmux), and the server began **after the current boot began**. What `tmux list-panes` answers is
     never taken as proof, because it only describes the one socket asked (an agent under `tmux -L name` keeps its record while its
     server lives, even though the daemon's own tmux sees nothing of it). A record of a server from before this boot is the
     previous boot's and is never swept: it is what the boot step reopens. When the boot time is not known, or the process cannot
     be checked, nothing is removed;
   - the agent died and left a shell: the daemon (not a hook or the boot step, which look once) sees a pane whose foreground
     command is a shell (`bash`, `zsh`, `sh`, `fish`, ...) on three looks in a row, three minutes, **and no Claude Code anywhere
     below the pane's process**, and removes the record. A shell in front is not enough on its own: an agent started through a
     wrapper script that does not `exec` it, or stopped with Ctrl-Z, also leaves a shell in the foreground, and keeps its record. Only
     a shell counts, never "not claude" (a native `claude` can show its version as its name). The clock restarts if the agent is
     back. A resumed window whose `claude` was not found on the path is such a shell too, and its record goes the same way;
   - it is older than **seven days** (last seen), or its folder has been gone for a day. These are removed at the next boot.

   **Every removal except the age one fails closed.** The checks ask systemd twice (the system and the box user's manager) and
   remove only when **both** answer `running` or `degraded`. A timeout, a dead bus, an empty answer, `stopping`, `starting` or
   anything else means "may be stopping", and nothing is removed. The answer is asked again just before each removal, the daemon
   runs no sweep once it has been told to stop (not after waking from its sleep either), the records are read **before** tmux is
   asked (so a session that starts in between keeps its record), and a record is read again just before it goes and kept if it
   moved to another pane meanwhile. The price of failing closed: a person who ends a session while the user bus is unreachable
   leaves a record, which ages out in seven days or is removed by a later check.
2. **Only the record hooks are installed at boot.** The resume step, and the daemon when it starts, install four Claude Code hooks
   (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `Stop`) that run `ozboxd session-hook`. That command writes or removes the
   record and nothing else: it prints nothing, never asks about or denies a tool, and never talks to the daemon. They are recognised by
   what they run (`ozboxd session-hook claude-code`, at any path of the binary), not by a field Claude Code does not document, and the
   file is **written only when a hook is missing or points at another path**: a file that already has them is not touched, not even
   re-formatted, so Claude Code rewriting its own settings never starts a rewrite loop. When it is written: a symlinked
   `settings.json` is edited through to its target and stays a link; the file's own mode (and owner and group, where the process may) is kept (a new file is 0600); the order of
   the keys is kept and everything that is not ours stays the text it was written as (the file is edited as ordered entries of
   raw JSON, not through a sorting map; only a hook of ours that points at an old path of the binary is re-written, and then only
   that one group); and the write is a temporary file beside the target, flushed and
   renamed. The file is stamped (size, modification time, inode) before it is read and again just before the rename; if someone else
   wrote it in between, it is read again and the work redone (three tries), and then it is left alone and the journal says so. A
   settings file that exists but is empty is never taken for "no settings": it is left alone, because a writer that truncates first
   and writes after leaves exactly that for a moment. A file with the `hooks` setting twice is left alone. Leftover temporary files
   of ours (our own name pattern, older than an hour) are removed. Claude Code may show its "hooks changed, review in `/hooks`"
   prompt when the hooks are installed while a session is already running; that is expected, once, and is checked by hand in the proof. A file that is not valid JSON, not an object, or cannot be read is left exactly as it is, and the daemon's journal says
   so. Claude Code's folder is
   made when it does not exist yet, so the very first session is recorded. **The asks about risky commands (`git push`, `sudo`,
   `rm -rf`) and the Gemini and Codex hooks are not installed at boot:** they stay with the explicit `ozboxd hooks install`, as ADR
   0021 says. A supervised run (`claude -p`) is not in tmux, so the record hooks do nothing for it; a `claude -p` inside a tmux pane is
   ignored by the ownership rule above; and they never decide a permission. Only Claude Code is hooked at boot, because it is the only engine whose resume is proven; another engine that the
   person hooked with `ozboxd hooks install` is recorded and gets its window back with a line that says so.
3. **Resume at every boot.** A user unit, `ozbox-session-resume.service`, is **written by the daemon**, as the box user, into the
   box user's own systemd folder (`~/.config/systemd/user`, with the link in `default.target.wants` that `systemctl --user enable`
   would make). It is not in the first-boot template, so user data does not grow and **a box made before this release gets it too**:
   at the next start of its daemon after the upgrade is installed, with no root helper and no machine replace. It takes effect when
   the box user's manager next starts, which is the boot that follows a stop. The unit lives in the box user's own folder, so it only
   ever runs for that user (the first review's worry about root, `ssm-user` and the ingress account does not arise). The
   link is made **only the first time** (a marker in `~/.local/state/ozbox` says it was): `systemctl --user disable` removes it and
   it stays removed, and a mask (a link to `/dev/null`) or a replaced unit is left alone too. The unit's text is still kept current. It runs `ozboxd
   session-resume`: for each record whose tmux server is not the one now running, it recreates the tmux session and window and
   reopens the agent with its own resume, then moves the record to the new pane. A run twice does nothing the second time. It is
   ordered after the box user's manager, which is already held back until `/work` is a mount point. It always exits 0: a resume
   that fails must not leave the manager unhealthy.
   - **At most six sessions reopen per boot** (the newest first). Each reopened `claude` is a Node process of a few hundred MB, and
     the tunnel and the IDE start at the same time, so on the 4 vCPU / 8 GiB benchmark shape six keeps the boot clear of the
     out-of-memory event ADR 0045 exists to prevent. The rest stay recorded, are listed as "not reopened", and age out.
   - **The folder is data, never code.** tmux expands `#(command)` and `#{format}` in names and in `-c`, so nothing a folder or a
     window is called reaches tmux as text it expands: names are plain words (letters, digits, `_`, `-`, space; no `#`), the target
     is the exact match `=name:`, and the folder is a quoted argument of the window's own script (`cd -- "$1"`), never `-c`.
   - **The first tmux server of a boot starts in a scope of its own**, `systemd-run --user --scope --unit=tmux-spawn-ozbox-resume-<n>`.
     That puts the server, and the panes that do not move out of it, under ADR 0045's memory drop-in, which covers `tmux-spawn-`
     scopes (a soft `MemoryHigh` and `OOMPolicy=continue`), instead of the resume service's cgroup, where one kill would stop the
     whole service. **This is an assumption to check on a real box**, together with ADR 0045's own prefix-drop-in question: that the
     server's cgroup is `tmux-spawn-ozbox-resume-*.scope` and carries those limits. If a scope cannot be made, tmux is started
     inside the unit (`KillMode=process` keeps it alive across a restart of the unit) and the journal says so. The server process
     itself is not protected from the OOM killer by ADR 0045.
   - **Known gap, the terminal's own server.** If the dashboard terminal starts the first tmux server of a boot (before the resume
     step does), it starts it from `ozboxd.service`, in that service's cgroup, with its `NoNewPrivileges` and `ProtectSystem=strict`;
     the resume then adds its windows to that server, and the resumed agents inherit those limits and the service's cgroup instead of
     the `tmux-spawn-` scope. That order is rare (the resume unit starts with the box user's manager, before anyone opens a terminal)
     and is not fixed here: giving the terminal the same `systemd-run --user --scope` start changes how every terminal attaches, so
     it is its own change. The real-box proof checks the cgroup of the server it finds.
   - **Racing the resumed agent.** The resumed agent's first event can land before tmux returns, and `--resume` may give it a new
     id. So the resume moves the old record without calling it "seen" (an agent nobody uses still ages out) and without pruning,
     drops it if a record of the new pane already exists, and a plan keeps only the newest record of a pane.

   | Claude Code | `claude --resume <id>`, the id starting with a letter or digit so it can never be read as a flag (`claude_code::is_resume_id`, also used by supervised runs) | The flag is the one supervised runs already use. 5. **A resumed agent is offered the "you were interrupted, continue" message, never sent it.** ADR 0021's typing path (`/attach`) is
   audited and gated on the agent waiting, and boot is not a person. Nothing here types into an agent. The window prints the offer
   above the agent and the person chooses. Pre-filling the prompt without sending is possible later.

**What comes back, and what does not.** Sessions come back; running programs end. Lost: the turn in flight, background processes such
as dev servers, shell variables and scrollback, and a permission question that was waiting. The agent's conversation (its transcript,
on `/work`) is what the resume reopens.

**When it applies.** The resume runs when the box user's manager starts, so it covers a **reboot of the box**: a resize, a stop and
start, an upgrade that reboots, a crash that reboots, an out-of-memory event that ends in a reboot. An out-of-memory kill of one
agent, or of the tmux server, on a box that keeps running does **not** run it: those windows are gone until the person reopens them.
The boot step does not sweep: it runs inside the user manager's own start job, which answers `starting`, so the fail-closed check could never pass there; the daemon's minute check and the hooks do that work. When the minute check is skipped ten times in a row because a manager does not say `running` or `degraded`, the daemon logs one line naming both answers (and resets when a check is allowed), so a check that can never pass is not silent. Whether a process is Claude Code is judged by its name, by `/proc/<pid>/exe` (a native install started by its resolved path), or by its `argv`; `/claude-code/` counts only as the script of a `node` or `bun` process. The pane's own process (`#{pane_pid}`) is read in the same tmux call as the pane's place, and a place without it writes no record. At most 200 records are read, newest first.

Their records are removed by the daemon's check once the pane is gone (an agent killed in a pane that stays shows a shell and goes
after three minutes; a tmux server that ended goes at the next check), so a later reboot does not bring back what the person had
already lost. A box made before this release gets the unit and the record hooks when its daemon
next starts, but a Claude Code session that was already running then has no hooks (it read its settings when it started), so it is
recorded only after it is started again. A live update that restarts the daemon without rebooting installs the unit and hooks; the
resume itself still waits for the next boot.

**Turning it off.** One switch for the record hooks, the unit, the sweeps and the resume: create the file
`~/.config/ozbox/session-resume.off` (`mkdir -p ~/.config/ozbox && touch ~/.config/ozbox/session-resume.off`). While it exists, the
hook writes and removes no record, the daemon and the boot step install no unit and no hook and sweep nothing, and nothing is
reopened; hooks already in `settings.json` stay there and do nothing. Delete the file to turn it on; records from before the switch that are under seven days old are then reopened at the next boot. To stop only the boot unit,
`systemctl --user disable ozbox-session-resume.service` (it stays disabled), or the off-switch file; `systemctl --user mask --force ozbox-session-resume.service` also works (the unit is a regular file in the very folder `mask` links into, so a plain `mask` refuses with "File exists"; confirm on the real box). Taking the hooks out of `settings.json`
by hand is not durable: the daemon puts them back at its next start unless the switch is on.

**Not in this slice.** Quiesce before a resize or an upgrade is slice 2 (below). Supervised
runs resuming after a boot, upgrade phases 3 to 5, slots, and the memory plan shared by both spawners (Z1) are separate work. The
docs must not say sessions survive a resize until a real-box resize with a Claude Code tmux session and a supervised run passes.

**Costs.** A resumed window runs the agent through an interactive login shell, so it sees the box user's profile (a `claude` put on
the path by nvm or a user prefix is found), not the old shell's environment. A record of a session the person ended with `/exit` or
`/clear`, or of a window closed while the box runs, is removed and does not come back; one whose agent died and left a shell is removed
after three minutes of that shell, and one whose tmux server ended in this boot at the next check. A record that cannot be
removed safely (systemd or tmux not answering) waits, and at the latest ages out after seven days. An agent run under a non-default tmux socket (`tmux -L name`) is
recorded with that server: if the unit is restarted while that server is alive, its window is made again in the default server
(rare: a restart of the unit, not a boot). **Reopening `claude` at boot, unattended, also starts that project's approved hooks and
MCP servers, which used to need a person at the keyboard**; the six-session cap bounds how many. A folder outside `/work` is not
recorded, so an agent started there is not brought back.

## Slice 2: quiesce before a resize or an upgrade

Preview, and not proven on a real box (`scripts/real-quiesce-proof.sh` is that proof). The line is unchanged: **sessions come
back; running programs end.** A resize stays in place (quiesce, stop, resize, start, resume).

**When.** Only when the plan contains `instance.stop` for a running machine, after the person confirmed. A dry run, a refused
prompt, a relabel and a stopped box never reach the box. `ozbox resize` and `ozbox upgrade` do it; so does the dashboard's apply
(it has no strict mode, and it does the waiting on a thread of its own: the first apply starts it and answers `quiescing`, the page
asks again, so the dashboard's one request loop is never held; a box that was not ready and is not an older agent is **not stopped**
there, with a 409 that says why, because nobody can be asked again in that request).

**Warn.** Before confirmation the plan carries what will end, read from the box (`GET /v1/runs`, `GET /v1/agent-sessions`, never a
change): supervised runs by program name, sessions by engine (Claude Code reopens; others get a window), and "everything else".
A box that cannot be asked is "could not list", never "nothing running". Everything the box says is stripped of control
characters and cut before it is printed.

**Stop runs cleanly.** `POST /v1/quiesce` starts a job in a thread (a snapshot plus a grace period is longer than the 8 s a
request on the socket may take), `GET` reads it, `DELETE` ends the hold. The job: refuse new runs (a hold that expires by itself
after ten minutes), drop queued runs first (so a run that frees memory admits none), SIGTERM to the processes in each running
run's scope, wait the grace (10 s, at most 60 s), then the run's existing stop (`cgroup.kill`), then it looks until the killed runs are gone (at most 2 s). It holds no lock while waiting.
Each run is reported: ended, killed, cancelled, finished, **exiting** (killed and not gone after the settling time) or
**not_stopped** (the kill failed); the last two count as not stopped, and a run is never left out of the report. A second `POST`
while one runs does nothing more; one soon after a finished job (30 s, unless a `DELETE` came between) is refused with 429, so a hold
cannot be renewed in a loop. Every `POST` and `DELETE` writes one audit line to the daemon's log (method, job, grace, strict).

**An older agent, and a 503.** A box whose agent predates this answers 404 or 405. The command then does **not** call the old
`POST /v1/checkpoint` by itself: that writes a visible branch `wip/<box>/<time>` and pushes it if the box has a push remote, which
the person did not agree to. It says plainly that the agent is older, that uncommitted work is **not** snapshotted and runs are **not**
asked to end. *Amended 2026-11-17:* it then refuses before anything changes, even with `--yes`, until the person names a choice:
`--legacy-checkpoint` (below) or `--no-checkpoint` (go on with none, never asked again). Neither is the default, because ADR 0002
says the plan decides what happens before the confirmation, and `--yes` only confirms what the plan said: defaulting to the old
checkpoint would push a branch the person never agreed to, and defaulting to none let a scripted `--yes` lose the checkpoint
without a word. A dry run is never refused. The old path is behind
`--legacy-checkpoint`, whose help and output say it writes a visible branch and pushes it where the box is set to push; it cannot be
combined with `--strict-checkpoint`, and `--strict-checkpoint` refuses an older agent. A **503** from a box of this release means
the service did not start, and is a failure, never "older": same wording, no fallback.

**Strict.** With `--strict-checkpoint` the box takes the snapshot **first** (90 s), and when it is incomplete the job ends before it
touches a run: no hold, nothing ended. When it is complete the runs end and a second snapshot (30 s) catches what they wrote last.
A refusal says exactly what had happened (no run ended / the runs listed already ended / it may have ended some) and the command
lifts the hold. A program that ignores the request and is killed after the wait is a *clean* outcome (killing is the designed
result); a run that could not be stopped, a snapshot that failed and a box that could not be asked are not. The same lift happens
on every other way out before the change is applied: a declined question, a failed upgrade, a failed apply (a guard that releases
on drop, disarmed once the change is applied), and the dashboard's failed apply.

**Time.** The whole job is bounded by `grace + 2 s settling + 120 s snapshot + flushes + a few seconds`, and the answer to `POST`
says how many (`bound_s`). The command and the dashboard wait that long plus 30 s, never less than a local default of the same
worst case. Inside the snapshot a hard deadline is shared by every git call (each is cut to what is left, no new repository is
started after it, retention is skipped, the final `sync` is at most 5 s), and a call ended by its timeout leaves nothing of ours:
its temporary index and that index's lock, and the lock of the one ref it was writing (named from the clock, so ours alone, and
removed only when its time shows it was made during that call). **`packed-refs.lock` is never removed**: git makes it, not this
code, and "it was absent a moment ago" does not make it ours; a person's or an agent's git may hold it now. A git
ended by the time limit gets SIGTERM first and removes its own lock. Temporary indexes older than
an hour from a killed run are swept the next time that repository is snapshotted.

**Cancelling, and the stop of the daemon itself.** `DELETE` while a job runs asks it to stop: the job looks at a cancel flag before
the hold, between the runs it asks to end, while it waits, and before any kill, and when it sees it the hold is lifted and
nothing more is killed (what already ended stays ended). The job stays `running` (with `cancelling: true`) until its thread has
seen the request, so a `POST` returns that job and never starts a second one beside it. The command's wait no longer gives up
after three failed polls: a dropped connection says nothing about a job that keeps going on the box, so it keeps asking until the
job's own bound plus the margin has passed, and without `--strict-checkpoint` it never stops the machine while the job may
still be writing. Ctrl-C during the wait or the second question lifts the hold before the command exits. The dashboard validates
everything (plan age, typed name, passkey, permission) on its **first** ask, and later asks for the same plan only read how the
box is getting on; a refusal or a dropped plan after the runs ended lifts the hold and says the runs may already have ended.

The machine's stop also ends the daemon (systemd sends SIGTERM). The daemon used to run the older checkpoint there, which writes a
visible branch `wip/<box>/<time>` and **pushes it where the box has a push remote**: a resize therefore did checkpoint, and the
promise "nothing is pushed" was broken one step after it was made (the first review's remark that a resize never
checkpointed was wrong). Now the stop takes the same **hidden snapshot** a quiesce takes (never pushed, hooks off, 40 s, well
inside systemd's default 90 s stop timeout, and it waits at most 10 s for a snapshot already running). The older pushing
checkpoint is kept only behind `checkpoint.push_wip_on_stop = true` (off by default; its documentation says it writes the branch and
pushes). **Every automatic path follows the same rule** (round-2 follow-up): the idle stop and the cloud-interruption watcher
take the hidden snapshot too (bounded to the same 40 s, hooks off, nothing pushed), and reach the pushing checkpoint only with
`push_wip_on_stop = true`. The remaining callers of the pushing checkpoint, decided one by one: the daemon's explicit
`POST /v1/checkpoint` keeps it (it is a command, not an event); a run's own pause still writes the local branch `wip/<box>/<time>` its resume needs (resume works from that local
branch alone) but **never pushes it** unless `push_wip_on_stop` is on (owner decision; the CLI asks the daemon with
`POST /v1/checkpoint?for_run=1`, and a box agent older than this change ignores the flag and still pushes); `--legacy-checkpoint` keeps it (the person asked for that agent's own checkpoint by name); and an upgrade or
dashboard change that does **not** stop the machine no longer asks for any checkpoint (nothing is at risk, so nothing is
saved or pushed). `scripts/real-quiesce-proof.sh` checks that no `refs/heads/wip/` branch appears and nothing reaches a remote.

**What is not saved, by design**. A repository whose top level is the box user's home folder, or that has
`.ssh`, `.aws`, `.gnupg`, `.config/gcloud` or a similar credentials folder at its top, is **not snapshotted**: in a home folder
everything is untracked, and the snapshot would copy keys and history into a git directory. It is reported as "not saved:
home/dotfiles repo" (told, not an error, so a strict stop is not refused for it). An untracked file over **50 MB** is left out and
counted in the report (never named). Snapshots older than **14 days** are removed, in our own namespace only, besides keeping the
newest 20.

**What is looked at.** Every git repository under **`/work`** (the box user's home is there, and so is `/work/repos`), up to four
folders deep, **including repositories nested inside another** (a submodule, an embedded repository, a linked worktree): each is
snapshotted on its own under its own `refs/ozbox/wip/`, with its own line in the report. Folders that start with a dot and
`node_modules` are skipped, links are not followed. A repository deeper than four folders is not seen. New files count whatever the
person's `status.showUntrackedFiles` is set to (the check passes `--untracked-files=all`). A clean-filter or Git LFS configured for a
repository does run, as it would for `git add`; hooks and the file-system monitor do not.

**Checkpoint (deviation from the decided default, with reasons).** The decided default was `git stash create` plus `update-ref`.
This slice keeps the one idea, a ref under `refs/ozbox/wip/<UTC time>` and no branch, but builds the commit the way the existing
checkpoint does: `read-tree HEAD` and `add -A` into a throwaway index, `write-tree`, `commit-tree`, `update-ref` (with an
all-zero old value, so it never replaces). `git stash create` takes untracked files only with a temporary index anyway, and the
plumbing shares the code the daemon's other checkpoints are proven on. It never pushes, even where the daemon's other
checkpoints are set to push, and it never touches the working tree, the real index (compared byte for byte in a test), the
branch, the stash list or the remotes. No hook, no `core.hooksPath` of the repository and no `core.fsmonitor` runs
(`-c core.hooksPath=/dev/null -c core.fsmonitor=false`; tested with `pre-commit`, `post-index-change`, `reference-transaction`
and a monitor script). Each git call runs under `timeout -k 2 20` (cut to the time left, see Time above). The ref name comes from
the clock only (`-02`, `-03` after a same-second repeat, two digits so the names sort in order). The newest 20 per repo are
kept, and only under that prefix. Ignored files are not saved. **Restore, without overwriting newer work:** in the repository,
`mkdir ../recovered && git archive <ref> | tar -x -C ../recovered` makes a copy of everything the snapshot held (tested, with later
edits in the folder left alone), `git diff HEAD <ref>` shows what differs, and `git show <ref>:<file>` prints one file. The in-place
`git restore --source=<ref> --worktree -- .` replaces every file the snapshot holds **and removes files it does not**, so work done
after the snapshot is lost for good; it is documented only with that warning. `git stash apply` does not take it, because it is a
plain commit. A repo that fails is reported and the rest go on. Snapshots include untracked files that are not ignored (a stray
`.env.local` too) and stay reachable from `refs/ozbox/wip/*` until pruned, and a `git push --mirror` would carry them: delete them
with `git for-each-ref refs/ozbox/wip --format='delete %(refname)' | git update-ref --stdin`.

**Not done on purpose.** Nothing is typed into a tmux pane; the records of slice 1 already bring sessions back. Supervised
runs do not come back after a boot (their own recovery).

**Authorization.** The route is on the box user's socket, like the checkpoint and the run API. It is **not** on the dashboard
socket's table (`daemon_scope`): a dashboard that runs on a box cannot resize or upgrade it, so it has no use for it. A coding agent
on the box runs as the same user and could end its own programs anyway; the job ends a controlled run (one with a capability)
without its capability, which exposes only that run's lifetime, never its input or output. What a `POST` adds is the hold on new
runs, so it is audited and cannot be renewed more than once in 30 s, and the refusal a run start gets says how to lift it. `pause`
and `destroy` are not quiesced (the owner decision: resize and upgrade only).

**With ZDU-2 (draft PR #34).** That branch moves run spawning to systemd units. This code uses only the run API of this base
(`terminate`, `stop`, `cancel_queued`, the hold). After #34 the same three steps become: drop the queue, `systemctl stop` of each
run unit with `TimeoutStopSec` set to the grace (SIGTERM, then SIGKILL, in systemd's own order), and report the unit's result
instead of the exit code. The hold and the snapshot do not change. #34 is not merged here.

**Costs and benchmark.** A resize or upgrade waits up to the grace plus the snapshot (seconds for a normal tree) before it stops
the machine. No measured path changes: box create, resume, snapshot, destroy and exec are not touched, so no headline metric of
the benchmark moves. Runs started in the ten minutes after a quiesce are refused if the change then failed before the stop; the
command ends the hold itself when a resize or an upgrade fails or is declined before the stop, and so does the dashboard.
