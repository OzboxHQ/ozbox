**Decision.** Scheduled runs and webhook-started runs share three rules.

1. **A slot fires at most once, whoever is running.** Schedules and triggers live in one small JSON store. Taking the lease,
   checking it and claiming a slot happen together inside one locked read-modify-write. The lease has one holder at a
   time and an `epoch` that rises each time it changes hands or is retaken after lapsing. A claim is accepted only from the
   current holder with the current epoch, and a `<schedule>@<slot>` pair is written once. A dashboard that was paused and
   wakes after another took over carries an old epoch and is refused; two dashboards ticking in the same second fire one run.
   The store is one file on one computer, which makes two `ozbox serve` processes there safe; it is not a network store.
2. **Time is the person's.** A schedule is read in an IANA time zone (the owner's, chosen when it was made), shown as local
   time with UTC beside it, and follows daylight saving: a wall time the clocks skip runs just after the jump, one they repeat
   runs once. Plain language ("every weekday at 9am Lagos time") becomes cron, and the next five runs are shown before saving.
   A missed run is made up once if it is still inside a window (two hours by default) and otherwise skipped with a notice,
   never replayed as a burst. A schedule never overlaps itself (the new slot is skipped and noted). A paused target box is woken
   for the run and left to its own auto-pause, and the cost of that is shown.
3. **Inbound events are signed, bounded and treated as data.** The only way in is `POST /hooks/<trigger id>` on the
   dashboard's own public address, through the tunnel; no box opens a port. A request needs a valid HMAC-SHA256 signature made
   with the trigger's own secret (GitHub's header, a generic timestamped scheme, or a Stripe-style one), is size-limited and
   rate-limited, and a repeated delivery id or a stale timestamp is refused. An unknown, disabled or badly signed request
   gets the same answer. The payload never becomes part of the instruction: the instruction names fields, and their values and
   the payload reach the agent only inside a fenced block that says it is untrusted. The secret is shown once and is
   write-only afterwards.

Runs start only through the run system's `RunSpec` and `start_run`; the scheduler keeps no run machinery of its own. Until a
run system is connected the scheduler records a plain failure rather than pretending.

**Why.** A schedule that double-fires spends money twice and a webhook that is trusted is a remote control for an agent that
holds credentials. Both failures are quiet, so each rule has a test.

**Cost.** Failover between two computers needs a shared store, which this file store is not; a replicated store replaces it
behind the same lease and claim calls. A redelivery of the same GitHub delivery id is refused as a replay, so a person who
wants to try again sends a new delivery.

**Addendum (2026-11-10): two computers.** The lease and claim rules above now also hold across two computers, which a file on
one computer could not give. The same document can live in one shared object (an S3 object, reached through the AWS command
line) written with compare-and-swap: a writer that loses a race reads again and redoes its change, so the lease, the epoch and
the claims behave exactly as they do for two processes on one computer. A taker never compares the holder's clock with its own.
The holder bumps a `beat` counter on every renewal; each would-be taker records, in the document, *its own* clock reading the
first time it saw each beat, and takes over only when the beat has not moved for a full lease by that same clock. Computers
whose clocks disagree by hours therefore neither steal a live lease nor wait forever on a dead one. A holder cut off from the
object cannot renew or claim, and its old epoch is refused when it returns; the slots it already fired are never fired again,
and the slots it missed are made up by the new holder under the catch-up window. Failover is off until a person sets it up
(`ozbox schedule failover set s3://bucket/key`); the cost is a bucket the person owns, a call to it on each tick, and a takeover
after a crash that takes one lease (30 seconds) plus a tick.
