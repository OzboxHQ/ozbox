This is a public, high-level sketch. It will grow as components are built.

```
 you (any device) ──identity-checked tunnel──▶  Oz Box
                                                 ├─ ozboxd        box daemon: health, sessions, idle/pause
                                                 ├─ agent engine  your chosen coding agent, supervised
                                                 ├─ web IDE + desktop browser
                                                 └─ /work         persistent disk: repos, caches, scratch
 ozbox CLI / API ──▶ control plane ──▶ provider modules ──▶ cloud or VPS
```

- **Rust** for the CLI, the daemons and the engine adapters; **TypeScript** for the dashboard.
- **gRPC** between components; **REST and webhooks** for integrations.
- **Immutable image, persistent disk:** upgrading a box means a new image on the same work disk.
- **No inbound network:** every connection is a tunnel the box dials out to.

## Infrastructure

Infrastructure is code under `infra/` (see `infra/README.md`). An **image** is built once with Packer (Ubuntu 24.04 plus the
web IDE, desktop and tunnel client, every download pinned and checksum-verified). A **box** is an OpenTofu module per provider
(`aws-box`, `hcloud-box`) that boots a machine from an image with a separate encrypted `/work` volume. Shared cloud-init mounts
`/work` without ever reformatting existing data. Modules open no inbound port: AWS security groups have zero ingress, no public
IP and IMDSv2 only; Hetzner firewalls have zero rules. `tofu test` with mocked providers enforces this in CI, together with a
structural guard against any inbound rule. Each module's variables and outputs are the interface the provider adapters use.

## Crates (v0.1)

- `ozbox-core` - types, the `Provider` contract, and one shared planner (`Engine` over a primitive `Backend`) so every
  provider plans identically; `TofuModule` runs a box module through OpenTofu.
- `ozbox-provider-fake` - a file-backed provider (one JSON file, atomic writes) and the public `conformance` suite that
  every provider runs in its own tests.
- `ozbox-provider-hcloud` - Hetzner Cloud: lifecycle through OpenTofu, runtime actions through the REST API
  (`HCLOUD_TOKEN` read per call, never kept). Clone is unsupported (Hetzner cannot restore a volume from a snapshot).
- `ozbox-provider-aws` - AWS: lifecycle through OpenTofu, runtime actions through the `aws` CLI (no SDK).
- `ozbox-cli` - the `ozbox` binary: plan, show, confirm, apply for every mutation; `--dry-run`, `--yes`, `--json`.
- `ozbox-hubd` - the hub daemon on `main` (ADR 0042, Preview): runs as its own user `ozbox-hub` from a socket unit, checks and spools
  workers' signed, sealed messages for the supervisor, enrols workers (an invite, an attested request, then plan and apply), and holds
  no private key: the channel's keys are in the secrets service, which gives the daemon's socket only the handshake signature and an
  enrolment token's tag. It binds no network port (`RestrictAddressFamilies=AF_UNIX`).
  Its worker side, `ozbox-hubd agent` (Preview), dials out to the hub and runs what it is handed as a run of the worker's own box (queued in
  the box's task store and run by its supervisor), announces the worker's approval requests, and runs the worker's end of the conversation
  fabric, served to the box's tool host on a local socket.

## The box daemon (`ozboxd`)

One hardened systemd service per box (crate `crates/ozboxd`). It samples CPU, memory, pressure, disk, network and GPU every
5 seconds into a small on-box time-series store (live, per-minute for a week, hourly for 13 months); runs agent work in
memory-capped runs behind an admission queue. When the box user's own service manager is up and hands out memory and cpu limits, a
run is a unit of it (`ozbox-run-<id>.service`, whose program is a small shim that owns the run's output, standard input and exit
status), so a restart of the daemon is meant not to end it and the new daemon takes each one over from its record on `/work`; otherwise a
run is a cgroup scope under the daemon, which ends with it, and the self-test says which (ADR 0038, Preview: never run on a real box) behind an admission queue; pauses an idle box after saving uncommitted work as a hidden snapshot
(never touching the working tree, never pushing, no visible branch); saves the same on a cloud interruption notice (watched by a small service of its own, as the
user `ozbox-meta`, because only root and the machine's own services may reach the instance metadata service; ADR 0029); runs a self-test after boot, resize and
upgrade; tracks health incidents; and backs up `/work` with restic where the provider has no volume snapshots. Its API is a
Unix socket only — nothing on a box listens on a network port.
The daemon has two sockets (ADR 0040, decision 3). The box socket (`/run/ozboxd/ozboxd.sock`, group `ozbox`) is for the box user and
what runs as it. The dashboard runs as `ozbox-supervisor`, which is not in the box user's group, and gets a socket of its own
(`/run/ozbox-supervisor-api/daemon.sock`) that answers one user and one table of routes: health, metrics, self-test, incidents,
sessions, runs (list, start, log, input, cancel), files (read, and the writes inside the files jail), a checkpoint and the
terminal. systemd binds that socket as root in a folder root owns and hands it to the daemon, so nothing the box user does to
its own folders changes who may connect; the box user cannot connect, and the daemon also checks the kernel's peer credentials
(`SO_PEERCRED`) for the supervisor's uid on every connection. The table is one list in `ozbox-core` (`daemon_scope`), shared by
the daemon that enforces it and the dashboard's local agent, which sends nothing else and falls back to nothing. **The table
narrows the API, not the authority:** run start and the terminal already act as the box user, so whoever controls the dashboard
has that authority; the protection is that the box user cannot reach the dashboard. A run started on it passes the same
admission, caps and per-run token as one started on the box socket, and every request on it is logged with `via=supervisor`, the
route's name and the outcome, never its path or body. No socket answers an agent's permission request; until a caller exists, the agent's hook hands the question back to the person in their own terminal. The daemon is handed the socket only if it declares that it takes one.
A supervised agent run on a real box goes through that API (ADR 0019): the prompt is the run's standard input, and a run is
given a per-run token and the address of the credential broker, never a provider key. The broker runs in `ozbox serve` on the
operator's computer, so a reverse forward (`ssh -R 127.0.0.1:<port>:127.0.0.1:<port>`) over the connection already open to the
box makes that one port answer on the box's own loopback address only; no port is opened to anything else.

## The web dashboard

A single-page app (`packages/dashboard`: React, TypeScript, Vite, Tailwind) served by `ozbox serve`, which embeds the built
files in the binary. It listens on a loopback address only and requires a random per-start access token on every API call
(`/v1`), answers same-origin requests only, and sends no CORS headers. Every change follows plan, then apply: a button asks the
server for a plan, shows each change with its risk in a sheet, and applies only on confirmation; a change that cannot be undone
also needs the box name typed. The server applies only plans it issued itself, once each. Usage numbers from the demo provider
are labelled simulated; a figure with no data behind it is shown as a dash, never invented.
The dashboard also lists runs, pending plans (approvals) and an activity trail, refreshes live over a server-sent event
stream, installs as an app (its service worker never stores API data), and offers an "Open in" menu that shows how to
connect a desktop coding app to a box over SSH through its tunnel.
A slow cloud or box never holds the rest of the dashboard: the box list is shown from the last read, with its age, while a new read
runs, and a box that does not answer is reported as not reached.

### Reaching it from elsewhere

The server never listens on anything but loopback. To open the dashboard from another computer, run it with
`--public-url <address>` and an outbound tunnel you bring yourself (`--tunnel cloudflare`, `tailscale-funnel`,
`tailscale-serve`, `caddy` or `ngrok`; see [ADR 0010](/adr/0010-bring-your-own-tunnels)). With a public address the local
token is replaced by sign-in: a passkey, or an identity-aware proxy whose token the server verifies, and the server refuses to
start a public address that has neither. The address is the single source of the passkey's relying-party id, the allowed Host
and Origin, and the session cookie's scope. Settings, Dashboard access shows the tunnel's state and has a guide for each
provider; `ozbox tunnel status --json` says the same on the command line. `ozbox dashboard install <box>` runs the dashboard
and its tunnel as a service on a box: it stages the settings, and the root helper runs the box's own program as the
supervisor user from a system unit (ADR 0023, Amendment 1). The helper installs the settings only after checking they are the ones the person's computer sent, and only when the dashboard has none to read (a box whose system disk an upgrade replaced keeps its folder on `/work`); settings it already has are kept, because the box user can make the same request. It reports success only once the dashboard stays up and answers on its port. The dashboard then goes down whenever that box is upgraded or paused.

### Who may do what at the dashboard

Behind a sign-in each person has a role: **owner** (everything, including settings, permissions, secrets, costs and roles),
**member** (the work: runs, approvals, the browser, a box's terminal, files and IDE) or **viewer** (look only). One place
judges every request (`App::guard`): a table says what a request needs and the permission engine's `decide` answers for the
role, so no route carries a check of its own, and a route that changes something and is not in the table is an owner's. The page
reads the role and the list of what it may do from the sign-in status and shows only that. The first person on the list is the
owner; an owner changes a role with a passkey, and it is audited ([ADR 0039](/adr/0039-dashboard-roles-owner-member-viewer-and-one-rule-for-a-dashboard-with-no-sign-in-on-a-box)).
One function also decides whether a request counts as a person's second factor, so a dashboard with no sign-in on a box is
refused everywhere one is asked for.

### Telegram (Preview)

The dashboard server hosts one **Telegram bridge** (ADR 0050, phase P1): an outbound long poll of the Bot API on a thread of its own
(no inbound port, no webhook), reading `message` updates only. The bot token is a secret in the secret store, read for each call and
never kept. What a message may do is decided by one pure function in `ozbox_core::chat_policy`: a closed table of acts, one parser
that turns a message into exactly one of them, and `decide`, which returns `Allow`, `Handoff` (a link to the dashboard, nothing
done) or `Refuse`. An `Allow` can only be made by `decide`, and the executor asks again with fresh facts just before it acts.
Identity is a **link**: a Telegram numeric user id bound to a person by a passkey assertion made in the dashboard, and what a link
may do beyond reading is a **delegation**, a signed record whose digest is the WebAuthn challenge. The server keeps the evidence and
checks it again every time it is used, so a hand-edited row grants nothing. Links, delegations, the replay set of `(bot id,
update_id)` and the poll offset live in a file of their own, written with a sync before the act they allow; every act and refusal
is an audit entry, and what was said is kept in a sealed, 30-day, per-link transcript. In P1 only reading and talking to an agent
exist; talking goes through the chat gateway's own code, unchanged. Box power, `/run` and the chat profile on the box are later
phases.

## Supervised agent runs

A run is one agent doing one job on one box: an engine, a prompt or skill, the box, optionally a repository and branch, caps
for time, spend and tokens, and where the result goes. Everything that wants a run (a person, `ozbox run start`, a schedule,
a trigger) builds an `ozbox_core::run::RunSpec` and calls `RunStarter::start_run`, which validates it and queues a task in the
task store (one JSON file, written atomically under a lock, so the CLI and the dashboard server see the same state). A
supervisor admits queued tasks per box by free memory and a size cap (XS 1, S 2, M 4, L 6, XL 8, XXL 16 at once; the rest wait),
shows a live log, and saves work to a `wip/` branch whenever a run pauses. A run that reaches its time, spend or token cap
pauses at a safe point, checkpoints and asks a person to add budget or stop; nothing is lost. Fleet and per-person monthly caps
work the same way. Actions that need a person's yes (a push to a protected branch, a pull request into one, a command on the
ask list, an outbound message, spend above a threshold, anything touching a production-tagged resource) become approval
requests that show the exact action, reach people through the alert routing, expire if unanswered, and, in sign-in mode,
need a fresh second factor for the risky kinds. Every decision is recorded in the audit trail. The task board, the approvals
inbox and their settings in the dashboard, and `ozbox run` and `ozbox approvals` on the command line, all use the same
`/v1` calls.

An engine is an adapter (`ozbox_core::agent_engine::AgentEngine`): Claude Code (`claude_code`), and Codex CLI and Gemini CLI
(`codex_cli`, `gemini_cli`, over `headless`, which starts one process per turn and resumes the program's own session for the
next message). Each starts its program through the box daemon with the task on standard input and only its own vendor
family's credentials in the environment. What any engine reports is translated once into the engine-neutral turn model
(`ozbox_core::engine_turn`: task, ask, reply, tool use, usage, state, result), which is also what the hub carries in its own
message kinds, so agents on different engines and providers work one task without either seeing the other's program, vendor
or keys (ADR 0056).

## What an agent can do on a box

A run on a box reaches its working tools over MCP, from the same server as the orchestration tools: a shell, git, files, a
browser for the box's own previews, CI and Staging reads through a project's declared commands. Each call is decided by the
permission engine (modes, rules, scopes, and a grant for anything that changes production): it goes ahead, asks a person
through the approvals inbox, or is refused, and the tool, its group and the decision are written to the tamper-evident audit
log, never the command, the path or the output. Everything an agent can name is under the box's `/work`. The decision is
ADR 0026; the Permissions page shows each tool's decision for a sandbox, staging and production.

The browser tools (ADR 0037) drive a headless Chromium through a worker that runs on the box as a *controlled run*: the daemon
gives the server that started it a capability and answers the run's input, output and stop only to that server, and every
line between the two is sealed with a key made for that session. A step the worker judges risky runs only with a grant that
a person's decided approval becomes; everything the page loads or sends is judged at its destination by the worker.
On a box where the dashboard runs as its own user, the worker, its Chromium and its profiles run as a Unix user of their own
(`ozbox-browser`): a root launcher, reachable only by the dashboard's user, starts the worker inside a systemd sandbox and
hands the connection to it as its input and output, so the sealed channel is still the only way in and nothing new listens.
The profiles are in a folder only that user opens; the recordings and released documents are readable by the box's group.

**Agents talk to each other and to people (ADR 0057, Preview).** The same tool server offers every agent five messaging tools
(`messages_post`, `messages_get`, `messages_thread`, `messages_ack`, `participants_list`). Messages wait in ordered mailboxes held by
the hub (`main`), one per participant (`agent:<box>/<session>`, `person:<id>`, `group:`, `fleet:`). A worker box keeps a replica of its
own agents' mailboxes and queues their posts; the two talk over the hub's transport as their own profile of the signed, sealed channel,
under a `<box>.fabric` endpoint. The hub also sends each worker the approved memory notes and approved skills its agents may read, and
takes their memory proposals back for a person to review. A chat gateway posts a person's message in as that person and collects the
agents' replies. A message is data: nothing in the fabric approves, grants or releases anything. The fabric is attached to the server of a box that is a hub (ADR 0042, "Integration"; Preview).

## Secrets

Anything that must stay secret (provider keys, channel tokens, the tunnel token, backup credentials, internal token keys,
`.env` keys for a project) goes into one encrypted store, never a plain file. Each secret is sealed with its own data key
(AES-256-GCM) and that key is wrapped by a key-encryption key held outside the disk: AWS KMS for a fleet, the keychain on a
laptop, the TPM or an operator-typed passphrase on a server. The seal is bound to the store, the box and the name. On a box
the store belongs to a separate system user; the box user and the agents that run as it reach it only through sockets that
let them write a secret or ask for a token's tag, and a program that needs a secret is started by that user with the value in
its environment alone. Session ids, setup codes and tickets are kept only as keyed hashes. `ozbox secrets status` lists names
and ages; `rotate-kek`, `rotate-data-keys` and `rotate-hmac` rotate the three kinds of key. The decision is ADR 0018.

A change to the box's secrets needs a fresh second factor (a passkey in the dashboard, or a key in the laptop's keychain).
The first one is never enrolled from inside the box: `ozbox create` pins this computer's key in the box's first-boot
configuration, which root writes to `/etc/ozbox/approval-keys`, and the secrets service enrols it once. The store's copy on
`/work` (kept so an upgrade does not lose it) is ciphertext only; a box that keeps its key in a file escrows that key in its
own vault, and backups never hold the copy (ADRs 0028 and 0029, their latest amendments). The service's state file says
what protects the store and whether it is escrowed, in lines a program reads; `ozbox upgrade` reads it before replacing a
system disk, and the root helper's `recover-secrets` accepts only the service's own "lost with no escrow" with the pinned
key's signature (ADR 0029, Amendment 8).

Your computer reaches a box's secrets service through one route: the `ozbox-ingress` account, whose sshd block forces a single
command and whose key file only root can change, onto a third socket of the service that only that account and the service may
enter. Every request is sealed (HPKE) to a key the service made; this computer pins the key and a changed one is refused. The
box user's own import socket no longer takes keys, declarations or approvals. A file-kept store key may be escrowed in this
computer's keychain and put back through the same account when an upgrade replaces the system disk. The off-box issuer for
Production (a function in your own account that alone may read Production) exists as logic and as an OpenTofu module, deployed
nowhere (ADR 0029, Amendment 9).
