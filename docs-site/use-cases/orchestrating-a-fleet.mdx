One coding agent, the **conductor**, works on the box that holds your main branch. During a heavy session you tell it to
give features to other boxes, and it does: a worker box for each feature, each on its own branch, with the files it owns
declared up front, the interfaces they share agreed first, a mailbox between them, and a merge queue that puts the work
back into `main` one feature at a time. You decide what is yours to decide, from the dashboard, a chat or your phone.

See [how to read the status](/use-cases#how-to-read-the-status). The orchestration model, the Oz Box tools, the merge queue,
the rules file and the dashboard page are built and covered by the test suite, with fake boxes and a simulated agent. None of
it has been exercised on a real cloud box with a real agent yet, so every example below is **Preview** at most
([ADR 0020](/adr/0020-orchestration-conductor-and-worker-boxes)).

**Defaults, all yours to change:** up to **3 worker boxes**, up to **3 sub-agents** inside each, **one spend cap** for the
whole orchestration, workers that are **clones of the main box**, merges **approved by you**. A rules file, or the request
that starts the orchestration, can only make these stricter than your settings (`ozbox orch settings`), never looser.

## 1. Two features on two new boxes, from `main`

**You want:** from your session on `main`, "build feature A on a new box with at most 3 sub-agents, and feature B on
another box", then come back when it is done.

Start the orchestration (or let your agent do it with the Oz Box tools):

```
ozbox orch start --goal "Add invoices and a CSV export to the shop app" --box main --conduct
```

Your agent then uses the tools it was given: `box_clone` to make `inv-a` and `inv-b` as copies of `main`, then `task_start`
for each feature, with a brief, the files it owns and a limit of three sub-agents. Each worker is a supervised run
([ADR 0014](/adr/0014-supervised-agent-runs)) on its own branch (`orch/<id>/<feature>`), so it appears on the
**Tasks** board and on the **Orchestrations** page.

**Underneath:** a box is made by plan-then-apply on your own provider, inside the limits; a plan that cannot be undone is
refused to the agent and left to you. **Status:** Preview.

## 2. Agree the shared interface before anyone starts

**You want:** the two features to agree on the API they share, so neither guesses.

The conductor publishes a **contract** (`contract_publish`: an API description, types or a schema, with the files it
describes) before it starts the workers. A worker reads it with `contract_read`, builds against it and may not change it or
claim its files. If the conductor publishes a new version, every feature that uses it is told, and the next time the
worker reads it, it has seen that version.

```
ozbox orch contract o1 --name "Invoices API" --kind api --body-file api.yaml --paths api/invoices.yaml
```

**Underneath:** a draft contract cannot be built against, and the same text published again changes nothing and tells no
one. **Status:** Preview.

## 3. Keep two workers out of each other's files

**You want:** no two workers editing the same area.

Each feature declares **claims** (files, directories or globs). Asking for an area another open feature holds is refused, or,
if your rules say `on_overlap: sequence`, the later feature waits for the earlier one to merge. A worker calls
`claims_check` before it edits a file it does not own and is told who owns it.

```
ozbox orch claims o1 f2 --declare "src/web/**" --check src/api/invoices.rs
```

**Underneath:** one function answers every check; the dashboard, the tools and the command line all use it. A doubt counts
as an overlap. Enforcement today is the tool and the worker's instructions; an engine hook that checks before each edit
arrives with the engine hooks work. **Status:** Preview.

## 3b. A worker needs a decision

**You want:** a worker that is unsure to ask, not guess.

The worker calls `worker_ask`, writes down where it stopped, and ends its turn. The question appears on the board and in the
mailbox. The conductor answers what it may; a question marked for you (or one the conductor passes up) waits for you:

```
ozbox orch answer o1 7 --text "Use the existing money type."
```

The worker is resumed from its saved branch with the answer in its prompt. **Underneath:** a worker that is a live
conversation is told at once; one doing a single job is resumed when it ends its turn. **Status:** Preview.

## 4. Approvals come back to you, with your passkey for the risky ones

**You want:** the conductor to approve the small things and send you the rest.

The conductor can decide a low-risk request of its own workers (by default, a command on the ask list). It can never decide
a push to a protected branch, a pull request into one, a message to someone outside, spend above your threshold, anything
tagged production, or anything that needs a second factor. Those go to you in **Approvals**, with your passkey where you use
sign-in. Every decision is in **Activity**, with who made it (`conductor:o1` or you).

**Status:** Preview.

## 5. The merge queue

**You want:** finished features to go into `main` one at a time, rebased, tested, and approved.

When a feature is done (`worker_done`), the conductor queues it (`merge_queue`) or you do, from the page. For each feature in
order the queue rebases it onto `main` in a separate worktree (never your own working tree), runs the test command from
your rules file, asks for the approval your policy needs, and pushes without force. A **conflict** or a failing test goes
back to the worker that owns it, with the file names, and the next feature carries on.

```
ozbox orch merge o1 f1
ozbox orch merge o1
```

**Underneath:** a worker pushes its branch to the repository's remote when it is ready, and the queue fetches it from there;
the steps are `git` commands run as argument lists on the conductor's box. The test lane box is not used yet: tests run on
the conductor's box. **Status:** Preview.

## 6. One spend cap that pauses, never kills

**You want:** a ceiling on what the whole orchestration spends.

The default is $50 for the whole thing, across every worker. At the cap the orchestration pauses, each worker saves its work
to its branch, and you get an urgent alert. Add budget to go on:

```
ozbox orch budget o1
ozbox orch budget o1 --add 25
```

**Status:** Preview.

## 7. Come back later

**You want:** to stop for the night and pick it up in the morning.

```
ozbox orch pause o1
ozbox orch resume o1
```

Pausing asks every worker to stop after saving to its branch. Everything is kept in the same store as your tasks, so it also
survives a restart of `ozbox serve`; resuming starts each paused worker again from its saved work. Merged workers' boxes are
paused automatically, and destroyed after the number of days you chose unless you keep them. A box you made yourself is
never touched. **Status:** Preview.

## 8. Write down how you like it done

**You want:** your house rules in the repository, so every orchestration follows them.

Put an `ozbox.orchestration.md` file in your repository: a small block of settings, then plain words the conductor and the
workers read.

```
---
max_workers: 2
max_sub_agents: 3
spend_cap: $30
merge_approval: person
conductor_may: ask_command
test_command: make test
on_overlap: sequence
worker: clone
---
Small commits. Never reformat files you do not own. Ask before adding a dependency.
```

```
ozbox orch rules ozbox.orchestration.md
ozbox orch start --goal "..." --box main --rules-file ozbox.orchestration.md
```

**Underneath:** the front matter is read, never run (a test command is a list of words), a key it does not know is an error,
and a rule that is looser than your settings is ignored and shown to you. **Status:** Preview.

## 9. A skill your agent follows

**You want:** your agent to plan the way you would.

The repository ships an example skill, `skills/orchestrate-features`: plan the features, publish contracts first, declare
claims, ask rather than guess, queue only finished work. Copy it into your agent's skills folder and change it. A skill is
guidance for the agent; the limits it can ignore are not in it, they are enforced by the server. **Status:** Preview.

## 10. Your own agent in your editor, or a different kind of worker

**You want:** to drive it from the agent you already have open, or to choose what the workers are.

On the demo provider the **Orchestrations** page says that its agents and its merge are simulated. A role that may not start
runs (a viewer) can read an orchestration but is not offered Start, Connect, Pause, Stop, a budget, an answer or a message, and
the page says why. If the list cannot be read, the page says so and why, and does not show an empty list.

In the dashboard, **Orchestrations → Connect an agent** makes a token for 12 hours and shows the MCP settings once. Your agent
gets the same tools as the conductor, and the same limits: it is never you, so it cannot decide what is yours to decide.
Runs that Oz Box starts get their own token automatically through `OZBOX_MCP_URL` and `OZBOX_MCP_TOKEN`.

For the workers, the default is a clone of the main box. `worker: create` (with a profile, size or provider) makes fresh
boxes instead, and `worker: reuse` uses idle boxes you already have, if your settings allow new boxes. **Status:** Preview.

## 11. Main as the hub: handing a task to a worker over a channel (Preview)

Today `main` reaches a worker through your computer's connection. The hub is the route that does not: a worker dials out to `main`,
every message is signed and sealed, and no box is opened to the internet. **Built and tested with fake boxes and a loopback network; no
box has a hub yet, and none has run on a real cloud box.**

- `task_start` takes `transport`: `hub` or `ssh`. On a box with a hub, `hub` is the default when the worker box is one of the hub's
  workers; otherwise `ssh` is, as before. On a box with no hub, `hub` is refused by name and nothing is added.
- Over the hub the task is handed to the worker at once, never started by the laptop route, and `task_status` shows what the worker
  reported (accepted, working, the commit it finished with) beside the feature.
- **A worker is never given a Production key in this release.** The hub refuses it, the worker refuses it again on its own, and the
  off-box issuer refuses a worker too. There is no setting that turns this off. A task also never names keys: a conductor that tries
  is refused and it is recorded.
- **A worker asks for development or staging keys by name**, only names its task declared. `main` checks the ask, the values are
  sealed to that worker's own vouched-for key, and only the worker's secrets service can open them; `main`'s hub never holds a value.
  The keys are deleted when the task ends, when they are revoked, and at once if the worker loses `main`.
- **The connection:** a worker dials `main` over your tailnet or the provider's private network. `main` listens only on a private or
  loopback address, never on a public one, and both ends prove who they are before anything moves. A lost connection is retried by
  itself, nothing is delivered twice or out of order, and a worker that has gone quiet shows as "not answering", never as "working".
- Every hand-off and every refusal is in the audit record, with names and never values.
- **Approvals come back to `main`.** A request filed on a worker (in this release, a guard override) appears in `main`'s fleet inbox
  (`GET /v1/approvals/fleet`) with the worker's name. You decide it once with your passkey; `main` passes your decision on, and
  **the worker checks it itself** against the approvers your laptop set on it. `main` cannot approve anything on its own, a message
  that says "approved" grants nothing, and Production on a worker is never decided from `main`.
- **The merge queue takes a worker's finished commit.** When a worker reports the commit it finished, the feature joins `main`'s merge
  queue with that commit. With `test_lane_box: hub:<lane>` the tests run split across workers on that commit, and the lane is never
  green while a test has no passing result; a worker that stops answering has its tests moved to another. A conflict or failing tests go
  back to the worker. Your approval to merge is unchanged.
- **The hub is integrated (Preview, tested end to end in CI, never run on a real box).** `ozbox-hubd setup <box-id> <address:port>` (as root, on
  `main`) sets up the hub daemon, which listens on a loopback or private address only; a worker joins with a one-use invite, an
  attestation from a registrar you pinned (your computer's, or the AWS claim service's) and proof that it holds the attested key,
  sent to the hub's own listener; you confirm the plan and it is on the roster, with no other step. It then dials out, takes tasks,
  runs them on whichever engine the task names, asks for staging keys by name, sends its approvals to `main`'s fleet inbox, and its
  finished commits go through the merge queue and lanes. Agents on different workers, even on different engines and providers, can
  message each other and share reviewed memory and skills (see [Agents that talk](/use-cases/agents-talk)). On a worker, a task is a run of that
  box's own supervisor (its Models routing, its credential broker, its subscription choice and its spend caps apply, and a task you stop on
  `main` stops there), and the worker's messages and memory go through its agent. **Your approvers reach each worker** with `ozbox hub approvers`:
  `targets` and `sync` on `main`, `sign` on your own computer. Your computer signs the passkeys your dashboard lists, one list per
  worker, and `main` only carries them: the worker checks your signature itself against an approval key the box already trusts, and
  refuses an unsigned, forged, older, expired or other-box list, so `main` cannot change who approves. `status` shows the version each
  worker holds. Re-sign with a higher version before the 90 days (or the days you chose) run out; an expired list decides nothing.
  **Not done:** none of this has run on a real box yet (that is the owner's run). The registrars are built
  (Preview, CI only; never run against real AWS or a real box); an AWS worker needs the claim service, which is not deployed.
- **The registrars that vouch for a worker are built** (Preview, CI only; never run against real AWS or a real box). On AWS a worker
  proves it is the EC2 instance it claims with the identity document AWS signs, checked against AWS's published certificate for its
  region, the account, the region, the instance's age and the one-use token. For Hetzner and machines you own, your own computer is
  the registrar: `ozbox hub attest` shows what it would sign and signs after you confirm, and refuses on a box. `ozbox hub repin`,
  as root on `main`, pins or rotates which registrars the hub trusts; with none pinned no worker can enrol (the self-test says so).
  Not done: the AWS claim service that would call the AWS check is not deployed, and the first real AWS-signed document is still to be
  verified.

Design: [ADR 0042](/adr/0042-main-as-the-hub-workers-reached-over-a-sealed-channel-keys-sent-only-by-name-and-every-approval-comes-back-to-main).

## What is not done yet

- **A real cloud box and a real agent.** Everything here is tested with fake boxes and a simulated agent.
- **A real worker's run.** The worker's run path is built (a task is queued as a run of the worker's own box and run by its supervisor) and
  tested end to end with fake programs; it has not run on a real box. The AWS claim service that would call the AWS registrar is not
  deployed. Section 11 is the part that is built.
- **Over the hub:** a laptop's decision on a worker, an agent's own permission asks (only requests in the worker's request book travel),
  and the lane's comparison of the test list with the base branch and its report merge. The check that a branch still points at the
  commit the lane tested is built, and the conductor box's merger reads the branch's head from the remote for it, so it rests on the actual
  head and not only the commit a worker reported.
- **A message into a worker that is mid-turn.** It is typed in only when the worker's run is a conversation; otherwise the answer waits until the worker ends its turn, then resumes it from its branch.
- **A claims check inside the engine** before each edit (an engine hook). The tool and the worker's instructions carry it today.
- The **stdio** transport for the tools.
- **Sub-agent limits inside the engine.** They are given to the worker as an instruction and bounded by the box's admission cap.
