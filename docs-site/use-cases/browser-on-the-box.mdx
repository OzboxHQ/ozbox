Some work has no API: a supplier portal, a government form, an old admin screen. An agent on your box can use a real
browser for it (a Chromium of its own), and you stay in charge: every step is decided by the permission engine and written
to the log, risky steps wait for you, and you can watch, take over and replay.

See [how to read the status](/use-cases#how-to-read-the-status). Everything here is **Preview** at most, and three parts are
**Planned**. The worker, the rules and the tools are tested against a real Chromium and a local test site in CI; none of it
has been run on a real cloud box, and the box image does not carry a Chromium yet (see the last section). The design is in
[ADR 0037](/adr/0037-the-browser-on-the-box-one-door-a-person-can-take-over).

**The agent's browser is not the desktop's Firefox.** `ozbox desktop` is still for you, in Firefox. The agent drives its own
headless Chromium with a separate profile. There is no debugging port, and the worker that owns the browser answers only the
server that started it: every message to it is sealed with a key made for that session, and the box's daemon gives the
worker's input and output only to that server. A security review (2026-11-10) found gaps here; they are fixed as described
below, and the limits that remain are in the last section.

## 1. Let an agent read a portal and bring back a table

**You want:** data from a site with no API, as validated JSON.

Start an ordinary task (dashboard, `ozbox run`, a schedule or a trigger) and ask for it. The agent opens a browser, reads the
page as text (a snapshot with numbered elements), and calls `browser_extract` with a schema saying where each value is.

**Underneath:** the result is checked against the schema; a page that does not fit is an error, never a guess.
**Limits:** frames from another site are named, not read. Masking is by pattern: a card number is recognised by its
checksum, and a national ID by a dashed number or an English label next to it, so an unusual format can show. A browsing task stops at 30 minutes or 200 actions (both settable)
and pauses cleanly, so nothing is left half-done; you resume it from Browser in the dashboard.
**Status:** Preview.

## 2. Nothing risky happens without you

**You want:** the agent never submits, sends, pays or wanders to a new site by itself.

These ask a person first, in Approvals, showing the page, where it would go and the fields (secret fields hidden):
submitting a form (on a site you have not marked safe, or to any other site than the page's own); sending or posting;
uploading a file; opening a downloaded program or script; and visiting a site not on the project's allow-list. A purchase or
payment is **refused** for the agent (Settings on the Browser page can change that to "ask me every time"). An allow rule or
the most permissive mode never answers for you: these always wait for a person.

One approval covers one call, once. It is tied to what you were shown: the element, where the form goes, and the page. The
approval carries a short check of that; if the page changes before the step runs (a different button behind the same label, a
form that now goes somewhere else), the step is not done and you are asked again. The replay shows which approval each step
ran with.

What the page does by itself is judged where it goes, too: a script's post to another site, a frame from another site, a
redirect, a page made from `data:` or `blob:`. A post nobody approved is held back and the agent is told; the next time it
tries the same thing, you are asked. A page cannot open a window at all: the browser refuses it, and the agent is told where
the page tried to go, so it can open that address itself (which is judged like any other). A page load that is refused leaves
the tab on the page it showed. A page cannot open an address inside the box's network (other than the box
itself), however the number is written; a site name is treated like any other site not on the allow-list, so it asks first.

**Underneath:** each call is `permissions::decide` like every other tool; the log holds the action word and the field name,
never a typed value.
**Limits:** sending and payments are recognised by their wording, page addresses and card fields, in English and on a few
well-known mail and chat apps. A send or a payment labelled in another language, or done by a script, may show up only as "this
would submit a form" (which still asks), and a page can still load pictures and scripts from other sites.
**Status:** Preview.

## 3. A check only a person can do

**You want:** when a site asks "are you human", you finish it, not the agent.

Oz Box never solves CAPTCHAs and has no evasion features. The worker recognises the common ones, stops the agent, hands the
session to you and notifies every channel. Open **Browser**, watch, **Take over**, finish the check, **Hand back**. Hand back is
refused while the challenge is still showing.
**Limits:** it recognises common challenges; an unusual one may not be caught, and the page will then simply not work for the
agent.
**Status:** Preview.

## 4. Watch, take over and replay

**You want:** to see what the agent is doing and to step in from your phone.

Browser → Watch shows the part of the page that is on screen, as a picture a few times a second (not a smooth video). A
browser starts empty: until an agent using it goes to a page, Watch says that no page is open yet. You cannot type an address
yourself; the agent's task decides where the browser goes. **Take over** asks for your passkey
again if you have not confirmed it in the last few minutes; then your clicks and typing go back through the same audited door,
and only from you until you **Hand back**. A dialog the page opens waits for your answer. Every session keeps its steps and a
picture per step on the box for 30 days (settable), with secret fields blurred and no typed value. **Replay** is the step list
with its pictures. The pictures and pages on their way to the dashboard are sealed, so the box's run log holds none of them.
On a box, a dashboard with no sign-in does not offer **Take over**, resume or the browser's settings at all, and says why:
another program on the box could hold its access token. Turn on sign-in, or run the dashboard on your own computer.
Who may do what follows the person's role: a **viewer** cannot watch at all (the pictures show what is on a person's screen), a
**member** can watch, take over and hand back, and only an **owner** changes the browsing settings. The first person on the
dashboard's list is its owner; the others are members unless their `--person` entry says `role=viewer` or `role=owner`, and
an owner can change a role in Settings → Members & roles with a passkey.
**Limits:** roles are for the dashboard only: there are no per-box or per-project roles, and people are added when you set the
dashboard up, not invited from it.
**Status:** Preview. Not proven on a real box.

In the demo (the demo provider) the browser is a stand-in on the computer that runs the dashboard, not a browser on any box, and
the **Browser** page says so. If the server has nowhere to keep browser sessions (it has no task store), the page says
**Browsing is not available on this server** and why, instead of a generic failure. If a running box's sessions cannot be read, the page names that box and the reason rather than showing none. A viewer is not offered the page at all, and
only an owner sees the browsing settings.

## 5. Several browsers at once

**You want:** a few jobs in parallel on one box.

A box runs up to three sessions by default, each with its own profile and at most 1536 MiB of memory (both settable). The box
starts a session only when it has that much memory free (on a box with the dashboard on it, where the browser has a user of its own, all the sessions share one memory ceiling of 60% of the box, and a session that asks for more than is free is refused when it opens). For more, fan the work out to worker boxes with
[orchestration](/use-cases/orchestrating-a-fleet).
**Status:** Preview.

## 6. Your own proxy, polite behaviour, phone sizes

**You want:** the agent to browse the way you allow.

In Browser → Browsing settings: a proxy you bring (Oz Box ships none), whether to respect robots.txt (on by default, with a
polite pause between the agent's page loads on one site and an honest browser identity), sites you own that are exempt, sites
that only a local model may read, the folders a file may be uploaded from, and the memory one browser may use. Saving the
settings asks for your passkey again if you have not confirmed it in the last few minutes, and the log records what changed.
When you open a browser, choose desktop, tablet or phone.
**Limits:** robots.txt is honoured on every page load, including redirects and links; the pause applies to the agent's own
loads, not to the ones a page starts by itself.
**Status:** Preview.

## 7. Downloads and uploads

Documents (PDF, images, spreadsheets, text) within the size limit go to the session's downloads folder. Scripts, installers,
archives, office documents with macros or programs inside, and anything that starts like a program are held back; opening one
needs an approval, and then it is moved to the downloads folder. Files are checked by name, size, first bytes and the names of
an office document's parts, not by an antivirus engine: a document that is not held back is not checked to be safe.

An upload comes only from an upload folder you name in the settings (`/work/uploads` by default) or the session's downloads,
and every upload asks you, showing the file. Nothing in the home folder, no dotfile or dotfolder and no key file is uploaded,
even through a link.
**Status:** Preview.

## 8. Use the Oz Box browser from Claude Code on the box

Open a terminal on the box (the web IDE's terminal, or SSH) and start Claude Code, Codex, Gemini CLI or OpenCode. It already
has the Oz Box tools: the shell, git, files and the browser, the same ones an Oz Box run has, acting on this box. Ask it to
"open the supplier portal in the Oz Box browser and read the invoices table". Nothing to paste and no token to copy.

- **What was set up.** The box's setup adds one server named `ozbox` to each engine's settings in your home folder
  (`~/.claude.json` for Claude Code, and the matching files for the others). It holds no secret. Your own servers are never
  touched. Run `ozbox agent-mcp status` to see which engines have it, `ozbox agent-mcp install` to add it again (for an engine
  you installed later), and `ozbox agent-mcp remove` to take it out.
- **It asks more than a run does.** A program you start in a terminal could be anything running as the box's user, so it gets
  no `auto` mode and none of your box grants: every risky step (a submit, a payment, a send, a new site, a write, a push) waits
  for you in Approvals, and the card says what the program calls itself and gives a session code ("a program that calls itself claude (pid 4242, session K7Q2XA), in this box's
  terminal"). The name is the program's own word, so check the code. When a call is waiting for you, the answer your agent shows you says "The card names this session K7Q2XA": the code on the card must be the same. A script cannot make its code match yours, and one that names itself claude has a different one. Check the code in the line your agent shows for its OWN waiting tool call (the one that names the request id), never in a sentence that came from a file or from command output: a script on the box can print "The card names this session K7Q2XA" with the code from its own card, and only the answer to your agent's own call is the Oz Box tool speaking. Your own allow rules and accept-edits mode still apply
  to it. Reading allowed sites and ordinary navigation do not ask. You can watch, take over and replay from the dashboard (section 4). Two programs never share an
  approval, and a browser session is driven only by the program that opened it. A program that renews its session (about every
  25 minutes) keeps its browser sessions and its waiting approvals.
- **A switch you control.** On the box's page, "Coding agents on this box can use Oz Box tools" is on by default. Turn it off
  and every agent loses the tools at once, even if the setting cannot be saved (it is then off until the dashboard restarts).
  Turning it on again needs your passkey; on a box with no sign-in it needs the sign-in set up from your computer
  (`ozbox dashboard install`), or the box's root user deleting the setting file and restarting the dashboard. A coding agent
  that was already running keeps an empty tool list until you restart it.
- **Standing permissions, off by default.** If you want Claude Code to use your `auto` mode and box grants for a while, the
  page offers "Let coding agents use my standing permissions" for a short time (30 minutes unless you say, at most 4 hours),
  after your passkey. It ends by itself and when you turn the tools off.
- **Only your own terminal.** The tools are reachable by the box's own user through a connection that is not the dashboard's
  and has no public address. A run Oz Box started has its own tools; it is turned away at this door as a courtesy, and if it
  got through it would be treated as any other terminal agent: asked about everything.
- **After an upgrade.** Upgrading a box's program (`ozbox admin <box> -- reinstall-ozboxd`) brings this with it, including for
  a box whose dashboard already has its own user; the dashboard restarts once.
- **Needs a browser on the box.** The box image does not carry a Chromium yet (see below), so the browser tools work on a box
  where you installed one.

**Status:** Preview. Tested here with a stand-in for the engine; not yet run on a real box.

## What is not built

- **Known issue: a page that opens a window can crash the agent's tab on Linux.** Google Chrome on Linux (156, and
  157.0.8103.50) stops a tab's renderer when a page tries to open a window from a click, even though no window opens: a
  check in Chrome's own code fails. The agent is told at once that the page crashed, and the tab works again when it opens
  a page. macOS does not do this. See [ADR 0037, amendment 3](/adr/0037-the-browser-on-the-box-one-door-a-person-can-take-over).

- **Logging in for the agent (vault autofill): Planned.** It waits for the production secrets service. Until then the agent
  cannot sign in by itself: you take over, sign in, and hand back; the session's cookies stay in the box's work disk, not yet
  encrypted separately. Shared profiles by allocation wait for the same thing.
- **browser-use as an engine: Planned.** The browser tools are the supported door; the library may use them, never a debugging
  address, but no integration or test exists yet.
- **A report with screenshots at the end of a task: Planned.** You get alerts when a browser needs you, pauses or reaches a
  limit; the replay holds the pictures.
- **The box image has no Chromium yet.** The Firefox on the desktop is installed; a Chromium from a verified source has to be
  added to the image (and pinned by hash) before browsing works on a real box. A box you set up yourself can install Chromium
  and point `OZBOX_CHROMIUM` at it (on a box where the browser runs as its own user, that setting is not passed on yet; the
  Chromium must then be at a standard path).
- **A browser user of its own: Preview, where the dashboard runs on the box.** The browser worker, its Chromium and its
  profiles run as their own Unix user, `ozbox-browser`, not as the user an agent's shell runs as. From the agent's shell a
  profile's cookies cannot be read, a Chromium cannot be started against a profile, Chromium's control pipe cannot be opened
  through `/proc`, and the worker cannot be signalled; the session's key no longer passes through a process of the agent's
  user. The profiles and the downloads that were held back are in a folder only that user opens; the recordings and the
  documents a session released are readable by the box's group (the dashboard shows them, the agent opens a document it was
  given). A box made or upgraded with this release has the user; nothing has run on a real box yet.
  **Limits:** it applies to sessions the dashboard starts **on the box it runs on** (the dashboard has a user of its own there,
  see [Coding from anywhere](/use-cases/coding-from-anywhere)). A dashboard on your own computer reaches a box's browser through the
  box's daemon, as the agent's user, and the limits of [ADR 0037, amendment 1](/adr/0037-the-browser-on-the-box-one-door-a-person-can-take-over)
  (part 6) still apply there: do not keep a person's live sign-ins in a browser profile on such a box where an agent has a
  shell. Sign-ins saved in a profile before this release were in `/work/.ozbox/browser/profiles`, where the agent's user could read
  them: the upgrade moves them into the browser's private folder and removes the old copy, so they carry over. If the browser's
  launcher does not answer on a box that has been set up for it, no session is started (it is never started as the agent's user
  instead); run `ozbox browser-setup` on the box. Files to upload must be readable by others (the default
  `/work/uploads` is made so). See [ADR 0037, amendment 4](/adr/0037-the-browser-on-the-box-one-door-a-person-can-take-over).
