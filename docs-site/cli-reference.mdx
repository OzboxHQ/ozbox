Run `ozbox <command> --help` for every option of a command. This page lists what each command is for.

## Options every change takes

Every command that changes something follows [plan, then apply](/adr/0002-plan-then-apply): it shows the plan, with cost and risk, and asks before it acts.

| Option | Effect |
|---|---|
| `--dry-run` | Show the plan and stop. Nothing changes. |
| `--yes` | Skip the question and apply. Not enough for a change that cannot be undone: that still asks you to type the box name. |
| `--json` | Print machine-readable output instead of text. |
| `--provider <name>` | Which provider to use. The default is the file-backed demo provider; `aws` and `hcloud` (Hetzner Cloud) are real clouds. |

## Boxes

| Command | What it does |
|---|---|
| `ozbox init` | Guided first-run setup: provider check, region, state bucket, private network, the fleet's secrets key (AWS; shown in the plan and created only when you approve), budget, alerts. A subnet already named in your configuration is used and no new network is planned; answering no to a step other than the state bucket skips it and goes on, and a summary lists what was applied, skipped and already in place. `--dry-run` previews every step, including the ones after a state bucket that does not exist yet (planned against an empty state; a preview cannot be applied). `--only <steps>` or `--skip <steps>` (repeat, or separate with commas: `state-bucket`, `network`, `secrets-key`, `adopt-command`, `operator-policy`, `box-policy`, `issuer`) choose steps without answering prompts; a step left out is said, and the state bucket cannot be skipped. On AWS the network's plan reads the Elastic IP and NAT gateway quotas and refuses with the numbers when there is no room; a step that only creates and fails part way removes what it made, and says so. Every step uses the same pinned AWS plugin version and one lock file. The operator policy file has the adopt step's own statements merged in, and the output lists which were added or replaced. A sign-in that fails because AWS is down or throttling says so and does not tell you to sign in again; an expired login or a missing profile each say the command that fixes it. Init edits the config file the program reads (`config.toml`, else `fleet.toml`), keeps its comments and keys, and never changes your daily `profile`. `--issuer-package <zip> --issuer-package-sha256 <hash>` also plans the off-box issuer for Production secrets. A budget is required before any box can be created on a real cloud (`--budget <dollars a month>`). |
| `ozbox create <name>` | Create a box. Options: `--size` (XS, S, M, L, XL, XXL, GPU-S, GPU-L), `--disk <GB>` for `/work`, `--image <id>` (default, Preview: the newest verified Oz image, yours or the project's public one for your region), `--tools`, `--profile`, `--label key=value` (repeatable). Once the box exists its SSH entry is written on this computer (`~/.ssh/ozbox/config`, so `ssh ozbox-<name>` works), as `ozbox connect <name> --ssh --write` would; the plan says so first, and `--no-ssh-entry` skips it. |
| `ozbox list` · `ozbox show <name>` | List boxes, or show one. |
| `ozbox sizes` · `ozbox providers` | The size catalogue and the machine type each provider maps it to, and what each provider can do. |
| `ozbox pause <name>` · `ozbox resume <name>` | Stop a box and keep `/work` (you pay only for storage), or start it again. |
| `ozbox resize <name>` | Change the size, grow the `/work` disk, or both. A disk can grow, never shrink. (Preview) A resize that stops the box lists what will end, ends its runs cleanly and saves uncommitted work first (a hidden snapshot, nothing touched); `--strict-checkpoint` refuses to stop it unless it was fully ready; on a box whose agent is older the command is refused before anything changes (even with `--yes`) until you choose `--legacy-checkpoint` (that agent's own checkpoint, which writes a visible branch and pushes it where the box is set to push) or `--no-checkpoint` (no checkpoint at all). |
| `ozbox snapshot <name>` · `ozbox clone <name>` | Snapshot `/work`, or create a new box from another box's latest snapshot. |
| `ozbox destroy <name>` | Delete a box and its `/work` disk. Asks you to type the name and keeps a final snapshot unless told not to: `--no-final-snapshot` for a throwaway box, and the plan then says no copy of `/work` is kept. Snapshots the box already has are kept and billed; the plan says how many and how to delete them first (`ozbox backup delete <name> <id>`). On AWS the plan also deletes the copies of old system disks the box's upgrades kept (each holds an old secrets-store key, and ozbox cannot list them once the box is gone); `--keep-old-system-disks` keeps them, and then deleting them is up to you. |
| `ozbox upgrade <name>` | Replace the system disk from a newer signed image, keep `/work`, then run the self-test. The plan names the kind of upgrade the two signed releases call for (live update, replace, or in place for a stopped box) and why (`--json`: `upgrade_kind`, with `called_for` and `carried_out`); every upgrade is still carried out as a replace, so `carried_out` is always `replace`. With no `--image` (or `--image latest`) it picks the newest image for the box's region whose signed release verifies: a newer image whose release was never published, does not list it, or is a pre-release a stable program does not use is passed over for the previous signed one, and the plan names each one passed over. An Oz image in your own account is used first, unless the publisher's newest signed public release is newer than it (and this program can use it): then the public one is used and the plan names your own image as passed over. If none verifies it refuses, naming `--image <id>` and `--allow-unverified-image`. An image you name whose signature cannot be verified is refused unless `--allow-unverified-image` is given. The plan says what happens to the box's secrets store; an upgrade that would lose it (a key kept in a file with no escrow), or a box that cannot be asked, is refused unless `--accept-new-secrets-store` is given. A box whose store is on the fleet's KMS key is refused an image whose secrets service cannot open it (a release before 0.2.0-beta.3, or a signed release that does not list `kms` in its `secrets_keys`) or whose release cannot be told; no flag lifts that. On AWS, when the store's key may be lost with the old system disk (a file key with no escrow, or a box that cannot say), the plan first keeps an encrypted snapshot of that disk (tagged `ozbox-purpose=pre-upgrade-root`, its id in the report and in `--json` as `old_system_disk_snapshot`) and prints a warning of its own before the confirmation (`secrets_store_warning`); `--no-pre-upgrade-snapshot` turns the copy off, and the old store can then never be opened. On AWS, a box already on the image has its machine replaced from the same image when the provider's record of its first boot (a tag the box cannot change) is not this program's, or is missing, or the box's own answer disagrees; `--reprovision` replaces it in any case, and an unfinished upgrade is finished first. On Hetzner an upgrade to a newer image replaces the server with this program's first boot; a box already on the image cannot have its first boot checked or repaired in place, and the upgrade says so. A signed AWS image whose release was built with a different first-boot configuration than this program renders is refused unless `--allow-first-boot-mismatch` is given (`ozbox create` checks the same). An upgrade that stops a running box gets it ready first, like `resize`: `--strict-checkpoint` refuses unless it was fully ready, and on a box whose agent is older the command is refused before anything changes (even with `--yes`) until you choose `--legacy-checkpoint` or `--no-checkpoint`. |
| `ozbox infra` | The box modules and first-boot configuration this program renders: its version, their hashes (`--json`) and the folder in use. The program carries its own copy; `module_dir` in the config is for developing the modules and needs `dev_modules = true` (or `--dev-modules`). |
| `ozbox adopt-fleet-key <name>` | AWS: move a box's secrets store from a key kept in a file on its system disk to your fleet's KMS key (`secrets_key_arn` and `fleet` under `[aws]`), in place, so an upgrade keeps the store and nothing is entered again. The box's role is allowed to use the key for the box's own secrets, the box re-wraps its own store (a copy while its service keeps running, then a short stop), and the box keeps its key file until the command has read the box's state as root through AWS Systems Manager (your AWS sign-in needs the statements in the operator policy that `ozbox init` writes to `operator-policy.json` on every run (an administrator applies that file; an older operator policy lacks them): `ssm:SendCommand` for your fleet's one document, which the program pins by its SHA-256, and `ssm:GetCommandInvocation`; never a shell, and no `ssm:CancelCommand`) and written the label that `ozbox upgrade` reads; until then an upgrade is refused. `--dry-run` shows the change; run it again if it stops; `--cancel` has the box record the cancel and take its store back under the file key, and removes the grant only after the box says it has. On a box that lost its label, `--cancel` offers the copy made before the move (it loses what was saved since) only when the cloud's tag list shows no label and the key service itself refuses the box, and you type the box's name. A box whose program is older than the feature is refused before anything changes: upgrade it first. |
| `ozbox adopt <name>` | Rebuild a box's infrastructure state from its cloud resources when the state is missing (AWS). It reads the cloud and never changes it. |
| `ozbox admin <name> -- <action>` | The one root path: `reown`, `reinstall-ozboxd`, `restart-services`, `collect-logs`, `enable-linger`, `ensure-supervisor`, `configure-box-secrets`, `recover-secrets` or `host-guard` (`host-guard memory install` puts the memory guard on a box made from this release that is already running, with nothing restarted; an older box gets it through the machine replace of its upgrade; `host-guard helper refresh` brings the root helper in step with the installed release). There is no shell; each action is recorded on the box, and the ones that need an approval say so. `recover-secrets` signs the box's one-time challenge with the key this computer pinned when it made the box. `replace-tunnel-token cloudflare|ngrok|ide --token-stdin|--token-from-store NAME [--approve-with-laptop-key]` puts a new tunnel token on the box, keeps the old one until the new tunnel is healthy and puts it back if it is not; the token is never an argument, and `--token-stdin` needs `--yes`. See [ADR 0011](/adr/0011-no-sudo-one-audited-root-path). |
| `ozbox capped [--max-gib N] [--soft] -- <command>` | On a box: run a command inside a memory cap (a production build, a test browser) so it can slow or end itself but never stall the box or kill your terminal. It never runs the command uncapped. See [ADR 0045](/adr/0045-box-memory-guard). |
| `ozbox backup` | List, run, restore, delete and schedule backups of `/work`, send the repository credentials to a box (`ozbox backup credentials <box>`), and turn a box's backups off (`ozbox backup off <box>`). |
| `ozbox tools` · `ozbox profile` | Install tools from the catalogue; save a box's tools and settings as a profile and create boxes from it. |

## Getting in

| Command | What it does |
|---|---|
| `ozbox connect <name>` | Say how to reach a box. With `--ssh` it prints the SSH entry; with `--ssh --write` it adds it to your SSH configuration, so terminals and desktop editors reach the box through your provider's tunnel with no open port. |
| `ozbox ide <name>` | The web IDE (VS Code in the browser), on `http://localhost` or on your own address behind your sign-in. |
| `ozbox desktop <name>` | A desktop with Firefox, the same way. |
| `ozbox open <name> --in <editor>` | Open `/work/repos` in a desktop editor over SSH: `vscode`, `cursor`, `antigravity`, `windsurf`, `zed` or `jetbrains`. |
| `ozbox ps <name>` | What is running on a box: tmux sessions, coding agents, listening servers. Stopping one is a change and is confirmed first. |

## Agents and their guardrails

| Command | What it does |
|---|---|
| `ozbox run start\|list\|show\|logs\|cancel\|retry\|resume` | Supervised agent runs with time, token and spend caps. A run that hits a cap saves its work and asks. |
| `ozbox approvals list\|approve\|deny` | What agents ask to do, and your answer. |
| `ozbox permissions show\|mode\|grant\|revoke\|check` | The default mode, the active rules, and time-boxed Production grants. |
| `ozbox audit list\|verify\|seal` | The tamper-evident audit log, and a check that nothing in it was changed. See [ADR 0022](/adr/0022-permission-engine-and-tamper-evident-audit-log). |
| `ozbox memory` · `ozbox skills` | Notes in git that agents read once you approve them; skills usable only after you approve their exact files. |
| `ozbox orch` | One conductor agent hands features to worker boxes, with claims, contracts, a mailbox and a merge queue. |
| `ozbox agent-mcp install\|remove\|status` | Give the coding agents on a box (Claude Code, Codex, Gemini CLI, OpenCode) the Oz Box tools, browser included: one entry in each engine's settings in your home folder, safe to run again, your other servers untouched. A box's setup runs it for you. Turn it off for everyone in the dashboard (the box's page). See [use the browser from Claude Code](/use-cases/browser-on-the-box). |
| `ozbox schedule` · `ozbox trigger` | Agent runs on a schedule in your time zone, or started by signed webhooks. |
| `ozbox models` · `ozbox cost` | Your model providers and which engine uses which model; usage and prices; the real cloud bill beside the estimate, and what in the account nothing uses. |

## Secrets

| Command | What it does |
|---|---|
| `ozbox secrets` | Report on the encrypted secret store (names and ages, never values), rotate its keys, import a project's `.env` keys (`--public NAME`, repeatable, marks a public URL or anonymous key that a declared command may receive as plain environment; it is refused for anything that looks like a secret; any value is stored, including spaces, quotes, JSON and several lines; only a blank value, a NUL byte, a value over 96 KB or an unclosed quote is skipped and listed by name). The `.env` file is read the way dotenv reads it: an `export ` prefix, single or double quotes (double quotes take `\n`, `\"` and `\\`), a trailing ` # comment`, and a quoted value over several lines. The result accounts for every entry (stored, held back, skipped with its reason, duplicate with the line kept, unchanged) and ends with a one-line total that adds up; `--json` carries it too. A name that appears twice keeps its last line. In a production environment `--allow-live NAME` (repeatable) or `--allow-live-all` (every production-looking key in the file; not together with `--allow-live`) allows production-looking keys, after the names are listed and a person at a terminal types the confirmation; from a script it is refused with the command to run. With `--box`, a box whose dashboard has a second factor gets an approval request for exactly the keys being sent (names and salted digests, never values) and the import waits while you approve it in the dashboard (**Approvals**, your passkey or, with no passkey, an authenticator code), then goes on by itself; for a non-Production environment it also offers to approve with this computer's key (`Approve it now? [y/N]`), never for Production. `--wait MINUTES` (1 to 30, default 30) limits the wait; Ctrl-C or a timeout stores nothing and the request expires by itself. `--approval CODE` (a code from the dashboard's **Settings**, **Secrets**) is the fallback, and the way for a box from before approval requests. `--dry-run` stops every `secrets` command that changes something: `import` shows its preview, `approve` makes no code. `ozbox secrets status` says how many values are stored encoded. `ozbox secrets ingress pin\|escrow\|setup-code --box <name>`: the sealed route to a box's secrets service. `ozbox secrets ingress requests --box <name> list\|show\|approve\|deny\|keys`: the change requests a box is waiting on, decided from this computer over the sealed route; `approve` needs the whole 64-digit digest `show` prints, and this computer's key is a software key, so it decides only what a member may, never an owner-only or Production change (use the dashboard and your passkey for those). See [ADR 0041](/adr/0041-one-approval-model-a-request-the-box-files-a-person-decides-and-the-box-hands-on). A Production import needs an approval from the dashboard, not this computer's key: `secrets approve --scope import --env production` says so and makes no code. |
| `ozbox env run\|policy` | Run a named command with only the secrets a project declared it may receive, on a closed network except the hosts it declared. `--pass NAME=value` gives a declared plain value; `--start`, `--stop` and `--status` manage a declared service (one that receives a secret gets it as a systemd credential, under the rules of a secret command, and a route to the project's declared `egress` hosts through a proxy unit that ends with it; `tcp` destinations are not given to a service yet); a declaration's `public` names receive values marked with `ozbox secrets import --public NAME`; `env policy pin --dir DIR --commit SHA [--entry FILE] [--tree PATH] [--tool NAME[=DIR] --release VERSION] [--browser NAME --browser-cache DIR | --revision KIND=N ...] [--arch amd64|arm64] [FILE...]` prints the digests to pin: files, folders, a script's whole import closure, a tool (fetched from the catalog's Linux release and checked against its checksum), browser revisions (Playwright's Linux build). Run it on your computer, in a clean checkout at the commit the box reports; on a box it refuses unless you add `--on-box`. `env policy set FILE --project P --box NAME` sends a declaration; a box whose dashboard has a second factor gets an approval request for exactly that declaration and the command waits while you approve it in the dashboard (**Approvals**, passkey or authenticator code; `--wait MINUTES`, 1 to 30); `--approval CODE` is the fallback (Preview). |
| `ozbox guard install` | Git hooks that stop a commit or push containing a key, and say the file, the line and the rule. On a box, a stopped change files an approval request and waits for a person to decide it on the dashboard; a code made for that exact change (`ozbox secrets approve --scope guard-override --project ... --env ...`) also works. A public web address or a `NEXT_PUBLIC_*`-style value is not a key (unless it has a user name and password, a query, or is a chat webhook) (a bare `PUBLIC_*` name is not taken as public; mark such a value with `ozbox secrets import --public NAME`), and a stored value shorter than 12 characters is not looked for. The hooks read the lines a change adds (binary and renamed files, merges and type changes included), the names of its files and the messages and headers of its commits and tags; a push is read against the remote it goes to (only when it pushes to the address it fetches from), and pushes up to 768 MiB are read in batches. A box with no second factor enrolled refuses an override and says how to enrol one. While a box's secrets service is not running, a commit is still read for the shapes of keys, the names of files and `.env` files and goes through if it is clean, with a note that stored values were not checked (the work is committed on the box and nothing is lost); a push is stopped until the service is back, and says how to bring it back. `ozbox guard wait <request-id>` waits, on a box, for a change request to be decided (Ctrl-C stops waiting and leaves the request, which lasts 30 minutes from when it was filed; a restarting service is waited for about a minute) and prints its digest when it is approved. |
| `ozbox box-secrets <name>` | Declare which non-production keys a box reads from your cloud's parameter store, into memory only. On Hetzner, a box with a second factor gets an approval request for exactly the declaration (and its vault address), and the command waits while you approve it in the dashboard; `--approval CODE` is the fallback (Preview). |

## The dashboard

| Command | What it does |
|---|---|
| `ozbox serve` | Serve the web dashboard on this computer only (loopback, with a random access token in the address). With `--public-url` and `--tunnel` it serves behind your own domain with sign-in instead of the token. |
| `ozbox tunnel setup\|status\|remove` | The outbound tunnel that reaches the dashboard from outside, with your own account. Supported: `cloudflare`, `tailscale-funnel`, `tailscale-serve`, `caddy`, `ngrok`. On a box whose dashboard has a second factor, `tunnel setup --approval CODE` (or `--approval-stdin`, the code on the line after the token) changes the token; the code comes from `ozbox secrets approve --box <box> --scope tunnel-token --project <provider> --token-stdin`. |
| `ozbox auth role <id> <role>` | Set a person's role from the command line, for an operator who cannot do it at the dashboard (every owner lost their passkey). Stop the dashboard first and start it again after; it refuses to leave the dashboard with no owner. |
| `ozbox auth init` | The sign-in settings for a dashboard on a shared machine: passkeys, or GitHub or Google followed by an authenticator code. Each `--person` starts with an id you choose (lowercase letters, digits and dashes, up to 32), never an email: the email goes after it (`jane,google=jane@example.com` or `jane,access=jane@example.com`), and an email given as the id is refused with the id to use instead. It can carry `role=owner`, `role=member` or `role=viewer`; the first person is the owner and the rest are members unless they say otherwise. |
| `ozbox dashboard install <name>` | Run the dashboard and its tunnel as a service on one of your boxes, as a user of its own: it reports success only once the box's root helper runs it that way, never as the box user. It goes down whenever that box is paused or upgraded. A later run with a new tunnel token changes only the token; on a box with a second factor it files an approval request for exactly that token and waits (up to 30 minutes) while you approve it in the dashboard (**Approvals**, passkey or authenticator code), with nothing to copy (Preview). As the fallback, add `--approval CODE` (or `--approval-stdin`) from `ozbox secrets approve --box <box> --scope tunnel-token --project <provider> --token-stdin`, with the same token piped in; a box from an image before this release takes a code made without `--token-stdin`. The public address is not changed by a later run. On a box that already has a supervisor, a run installs the sign-in settings it sent only when the dashboard has none to read, and keeps the ones it has otherwise: it still starts the dashboard if an upgrade left it stopped, and says so. To replace the kept settings (they decide who may approve) add `--replace-sign-in` with `--settings-approval CODE` (this computer's key never approves it; the code is made in the dashboard's Secret approvals with the binding the command prints); a box with no second factor refuses. |
| `ozbox dashboard retire-legacy-tunnel <name>` | Remove a tunnel an older setup left running as the box user, whose token file every agent on the box could read. Only once the box's own tunnel is up with connections of its own; the token is destroyed, not moved, so rotate it in Cloudflare afterwards. |
| `ozbox dashboard restore <name>` | Put the dashboard back from what this computer kept when it was installed with `--token-stdin`: the address, the people, the tunnel and its token (in the keychain, never a file). `ozbox upgrade` does this for you after it replaces the box's machine; its report says if the box wants your approval of the token and names this command. `--approve-with-laptop-key` makes that approval on the spot with the key pinned when the box was made, for exactly the kept token, the same step as `ozbox secrets approve --scope tunnel-token --token-stdin` (it is not made for a box whose helper does not tie a code to the token). `ozbox dashboard install --token-from-keychain` reuses the kept token instead of reading one. |
| `ozbox dashboard forget <name>` | Remove what this computer kept for that box's dashboard (its token and settings). Nothing on the box changes. |
| `ozbox mesh setup\|policy\|allow\|join\|status` | Reach your boxes over a Headscale tailnet you run yourself; the access rules are generated from your boxes and deny box-to-box traffic by default |
| `ozbox plugin list\|add\|approve` | Provider and tunnel plugins, run only after you approve the exact program |
| `ozbox telemetry status\|preview\|on\|off` | Optional anonymous usage counts; off until you turn it on, sent only to an address you choose |

```bash
ozbox auth init --origin https://dash.example.com --person you,label=You
printf '%s\n' "$TUNNEL_TOKEN" | ozbox tunnel setup cloudflare --public-url https://dash.example.com --token-stdin
ozbox serve --public-url https://dash.example.com --tunnel cloudflare
```
