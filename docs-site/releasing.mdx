How a release of the `ozbox` command line is built, signed, tested and published, and what the owner has to switch on
once. Nothing here publishes by itself: every real publish needs a pushed tag **and** an approval on a protected GitHub
environment.

## The tag scheme

One version, everywhere: the program, the box daemon (`ozboxd`) and the machine image share the single version in the
workspace `Cargo.toml`, written `MAJOR.MINOR.PATCH` and kept below 1.0 until the owner decides otherwise (`0.3.0`). A
program release is the tag **`vX.Y.Z`** (`v0.3.0`, `v0.4.0-rc.1`), and the machine image of the same product version is
**`image-vX.Y.Z`**, built by a different workflow from the same number. The `v` tag starts every package channel below, and
each carries the version `X.Y.Z`. A version with a `-` suffix is a pre-release: it is published to GitHub Releases (marked as
a pre-release) and never to Homebrew. The build date is only recorded inside the manifest (`built_at`), never in a version.

Before 1.0 a minor version may break anything and a patch never does. The program therefore refuses to upgrade a box to an
image whose major and minor version differ from its own, and says which of the two to upgrade (`release::compat`, tested).
An image that still carries a date version (from before this scheme) cannot be compared; it is allowed with a note. Every
release has a changelog entry (`docs-site/changelog/index.mdx`), which is what the documentation site shows.

`ozbox dashboard install --release` accepts `0.3.0`, `v0.3.0` (the program), `image-v0.3.0` (the image); the old
`cli-vX.Y.Z` spelling is still read. A release's version must equal the version in the workspace `Cargo.toml` (`ozbox --version` prints it); the release
workflow refuses otherwise.

## Channels: what exists and what is switched off

| Channel | What it gives users | State |
|---|---|---|
| **GitHub Releases + `scripts/install.sh`** | Signed programs for Linux and macOS (x86_64 and arm64), a signed manifest, checksums, and an installer that verifies them | Built. Runs on a `v*` tag after the owner approves the `release` environment |
| **Homebrew tap** | `brew install OzboxHQ/tap/ozbox` | Built, **off** until the owner creates the tap and sets `OZBOX_TAP_REPO` |
| **crates.io** | `cargo install ozbox-cli` | Workflow written, **off**, and **not viable yet**: see "crates.io" |
| **npm** | User-facing packages (for example a plugin SDK) | Workflow written; the list of packages is empty, so it does nothing |

The files: `.github/workflows/` has `cli-release.yml` (the release), `release-build.yml` (build, assemble, test the
artefact; reused by the release and by the dry run), `release-dry-run.yml`, `publish-homebrew.yml`, `publish-crates.yml`
and `publish-npm.yml`. The scripts are `scripts/install.sh` and `scripts/release/`. `packaging/npm-packages.txt` lists
the npm packages.

### What a release contains

For `vX.Y.Z`: `ozbox-linux-x86_64`, `ozbox-linux-aarch64`, `ozbox-darwin-aarch64`, `ozbox-darwin-x86_64`, each with a
`.sha256`; `SHA256SUMS`; the manifest `ozbox-cli-manifest.json` (version, source commit, dashboard hash, and one entry
per program with `os`, `arch`, `asset`, `sha256`); and for the manifest, the checksums and each program the Sigstore files
`.sig`, `.pem` and `.sigstore.json`. The Linux programs are statically linked with musl and run on any distribution. The
macOS programs are built natively by cargo on a macOS runner (the x86_64 one is cross-compiled by Apple's linker, not
emulated). They are not notarized; a program downloaded with `curl` or Homebrew is not quarantined, so Gatekeeper does
not stop it, but one downloaded with a browser may need `xattr -d com.apple.quarantine`.

The signatures are **keyless**: no key exists to leak. A signature proves which workflow produced the file, and the
certificate names `cli-release.yml` at `main` or a `v*` tag. `scripts/install.sh` and `ozbox dashboard install`
require exactly that. The signing job is therefore in `cli-release.yml` itself; do not move it to another file without
changing the identity both verifiers check.

cosign is pinned to **v2.5.3** in every workflow. cosign 3 no longer writes the `.sig` and `.pem` files that cosign 2
verifiers and the Rust verifier read, so do not raise the pin without re-checking `scripts/release/cosign-smoke.sh` and
`ozbox-core`'s `release.rs`.

## Installing (what users do)

Recommended: download the script, read it, run it.

```sh
curl -fsSLO https://raw.githubusercontent.com/OzboxHQ/ozbox/main/scripts/install.sh
less install.sh
sh install.sh                      # the latest stable release (it skips pre-releases)
sh install.sh --version 0.2.0-beta.0   # a named release, such as the Beta
```

Piping it to a shell works too, because the script verifies everything it downloads before it uses it. It checks the
manifest's signature with `cosign` (the certificate must name this repository's release workflow), checks the program's
sha256 against that manifest, and only then copies it to `~/.local/bin/ozbox` (`--prefix` or `PREFIX` to change it). It
never uses sudo and never runs the download before it is verified. Without cosign it **refuses**; `--skip-signature` goes
on with the sha256 check alone and says loudly that this only catches a damaged download. `--dry-run` shows what would
happen. Windows is not supported natively: use WSL.

## Releasing

1. **Dry run first.** Run the "CLI release" workflow by hand (Actions, Run workflow, a version, leave **dry run** on; it is
   on by default). The whole pipeline runs: plan, dashboard, four builds, manifest, and the artefact tests. Nothing is
   signed or published; the files are kept for 7 days as the artifact `release-out`. The "Release dry run" workflow does
   the same on every pull request that touches the release machinery.
2. **Test the packed artefact for real, before tagging.** The dry run already runs the Linux x86_64 program in clean Debian
   and Alpine containers and installs it with `scripts/install.sh` from a local release directory. Also do by hand what a
   runner cannot: download `release-out`, and on a real Mac run `ozbox-darwin-aarch64 --version` and `--help` (and the x86_64
   one on an Intel Mac or under Rosetta), then use the program for a minute. The mocked and structural tests never caught
   the worst bugs of other projects; a human using the exact file does.
3. **Set the version.** Make the workspace `Cargo.toml` version equal to the release (and each listed npm package's
   `package.json`), merge to `main`.
4. **Tag.** Push `vX.Y.Z` on a commit that is on `main`. The release workflow checks that.
5. **Approve.** The `release` environment waits for a reviewer. Approve it only after reading the plan job's log (version, and that it is a real release). The job
   signs, verifies its own signatures, creates the release as a **draft**, uploads everything, and only then publishes it, so
   nobody can fetch a release that is missing its signatures.
6. **Other channels.** `publish-npm.yml` and `publish-crates.yml` also start from the tag and wait for their own
   environments. For Homebrew, run "Publish Homebrew formula" by hand with the tag (GitHub does not start a workflow from a
   release that another workflow made with its own token). It opens a pull request on the tap; merge it after its checks.
7. **Verify after release**, on machines that did not build it:
   - a clean Linux box and a Mac: `sh install.sh` from the download-and-read steps above, then `ozbox --version`;
   - `cosign verify-blob ozbox-cli-manifest.json --signature ozbox-cli-manifest.json.sig --certificate ozbox-cli-manifest.json.pem --certificate-identity-regexp '^https://github\.com/OzboxHQ/ozbox/\.github/workflows/cli-release\.yml@refs/(heads/main|tags/v[0-9a-z.-]+)$' --certificate-oidc-issuer https://token.actions.githubusercontent.com`;
   - `brew install OzboxHQ/tap/ozbox` and `brew test ozbox`, once the tap is live;
   - `ozbox dashboard install <box> --release vX.Y.Z` still verifies and installs.

A release that went wrong is not edited: delete the draft or pre-release if it is not yet public, otherwise publish a fixed
`vX.Y.(Z+1)`.

## The benchmark gate (a release step, not CI)

Each image release is measured on the benchmark shape, 4 vCPU / 8 GiB / 40 GB (size XS), on a fresh box in our own account.
It needs a real box and costs money, so it never runs in CI. The scripts are in `scripts/benchmark/`; the first version
measures a documented subset with Oz Box's own parameters, so its numbers are comparable to this suite's earlier runs, not
to the leaderboard's.

1. Create the box: `node scripts/benchmark/lifecycle.mjs create bench-xs --out spawn.json --usd-per-hour N --usd-source "..."`
   (always XS with a 40 GB `/work`).
2. On the box: `scripts/benchmark/suite.sh --out cold.json --variant cold --guard on`, with the pins and tools named in the
   script header (`BENCH_MASTRA_REF`, `BENCH_BETTER_AUTH_REF`, `BENCH_GIT_REPO`, `fio`, STREAM). An item with no pin or tool is
   reported as unsupported, never as zero.
3. Warm variant: `lifecycle.mjs pause`, then `lifecycle.mjs resume bench-xs --out resume.json`, then `suite.sh --variant warm`.
   A warm result is its own variant and is never compared with a cold one.
4. Run the whole thing with the box memory guard (ADR 0045, which caps heavy runs at RAM minus RAM/8, 7 GiB on 8 GiB) both
   **on** and **off** (`--guard on|off`); each is its own variant.
5. For a result worth gating, repeat on several independently created boxes, then
   `node scripts/benchmark/gate.mjs merge --out merged.json FILE...` (medians; gaps stay gaps) and
   `node scripts/benchmark/gate.mjs compare --results merged.json`.

The gate fails (exit 1) when a headline metric is more than 10% worse than the stored baseline in
`scripts/benchmark/baseline/`, or has stopped being measured. It refuses to judge (exit 2) a box that is not the benchmark
shape, a missing baseline, or a variant mismatch; a first run is recorded with `gate.mjs record`, not passed. Headline
metrics: Mastra cold install, Better-Auth build, Git common operations, rand write 4KB O_DIRECT, STREAM Triad, spawn, resume
and USD per hour. Spawn and resume are the wall time until the `ozbox` command returns. No baseline is committed yet: it must
come from a real run.

## crates.io

**Not viable today**, and `publish-crates.yml` is off for these reasons:

- Every crate in the workspace is `publish = false` (an owner decision, not changed here).
- The crates depend on each other by `path` with no `version`; cargo will not package that ("all dependencies must have a
  version requirement"). The publish order is: `ozbox-catalog`, `ozbox-core`, `ozbox-memory`, the other crates in
  dependency order, then `ozbox-cli`; `scripts/release/crates-package-list.sh` computes it.
- **The dashboard.** `ozbox-cli`'s `build.rs` embeds `packages/dashboard/dist`, and a release build refuses to compile
  without it. A crate on crates.io contains only files under its own directory, so a `cargo install ozbox-cli` build would
  find no dashboard and either fail or serve the placeholder page. The dry run reports this every time.
  Every built program is then **run** and asked what it embedded (`ozbox build-info --json`, a hidden command;
  `scripts/release/check-embedded-dashboard.sh`): the build fails unless it reports this build's dashboard hash and no
  placeholder page. The programs are run natively, under qemu (arm64 Linux) or under Rosetta (x86_64 macOS). The file is not
  searched for the hash, because the compiler may store that constant in pieces.
- crates.io Trusted Publishing needs the crate to exist first (publish version one by hand), a trusted publisher
  configured per crate, and a human-reviewed pin for `rust-lang/crates-io-auth-action` (the workflow references it by tag
  with a comment; every other action here is pinned to a commit).

Proposed design, if the owner wants it: publish `ozbox-cli` and its sibling crates. In `ozbox-cli`, vendor the built
dashboard into the package (copy `dist` to `crates/ozbox-cli/dashboard-dist/` in the publish job, which the workflow
already does, list it in the crate's `include`), and make `build.rs` look there when `../../packages/dashboard/dist` does
not exist. Give each path dependency a `version = "..."` next to its `path`, and remove `publish = false` from the
workspace package only for the crates that should be public. Until then the supported install paths are the installer, the
Homebrew tap and a build from a checkout (`cargo install --path crates/ozbox-cli` after building the dashboard).

## npm

`packages/dashboard` is built into the program and is not published. `publish-npm.yml` publishes the directories named in
`packaging/npm-packages.txt` (empty today), each with `npm publish --provenance --access public` using npm trusted
publishing: no `NPM_TOKEN` exists. Before any publish it packs the package, installs the tarball in a clean directory and
runs the smoke command on that line. To publish a package: add `path :: smoke command` to the list, make its version equal
the release, and link the trusted publisher (below). `release-dry-run.yml` runs the same smoke test on every change.

## One-time owner checklist

Nothing below has been done by this repository's code.

**GitHub**
- [ ] Create the environments (Settings, Environments) `release`, `homebrew`, `crates-io` and `npm`. On each: **required
  reviewers** (the owner), and **deployment branches and tags** limited to the tag rule `v*` (and `main` for `release`,
  which a manual run may use). A publish that is not approved does not run.
- [ ] Settings, Actions: leave "Allow GitHub Actions to create and approve pull requests" off (the Homebrew job opens its
  pull request with its own token, in the tap repository).
- [ ] Branch protection on `main` once the repository is public: pull request required, the CI checks required, no direct
  pushes, no force pushes; tag protection for `v*` so only the owner can create one.
- [ ] Making the repository public, and squashing its history first, are the owner's decisions and are **not** done.

**Homebrew** (optional)
- [ ] Create the repository `OzboxHQ/homebrew-tap` (empty, with a README). Add a CI check there (`brew test-bot` or
  `brew audit --strict --online ozbox`).
- [ ] Create a fine-grained token (or a GitHub App installation token) limited to that repository with Contents and Pull
  requests write. Save it as the secret `OZBOX_TAP_TOKEN` of the `homebrew` environment.
- [ ] Set the repository variable `OZBOX_TAP_REPO` to `OzboxHQ/homebrew-tap`. Until it is set, the workflow does nothing.

**crates.io** (only after deciding on the design above)
- [ ] An account that owns the crate names; publish version one of each crate by hand.
- [ ] For each crate: Settings, Trusted Publishing: repository `OzboxHQ/ozbox`, workflow `publish-crates.yml`, environment
  `crates-io`.
- [ ] Review and pin `rust-lang/crates-io-auth-action` by commit SHA in `publish-crates.yml`.
- [ ] Remove `publish = false`, add versions to the path dependencies, vendor the dashboard (see above), then set the
  repository variable `OZBOX_PUBLISH_CRATES` to `true`.

**npm** (when the first package exists)
- [ ] An npm organization for the package scope; publish the first version of each package by hand (a package must exist
  before a publisher can be linked).
- [ ] For each package: Settings, Trusted Publisher: repository `OzboxHQ/ozbox`, workflow `publish-npm.yml`, environment
  `npm`.

**Docs site**
- [ ] Create the Mintlify project from the `docs-site/` directory and attach the domain; its publishing is separate from
  this release process.

## What was verified, and what was not

The install script is tested end to end against a local release directory (`scripts/release/test-install.sh`: refusal
without cosign, a stub cosign for the signature paths, a damaged download, wrong systems, pinning, the latest-release
lookup, dry run). The formula generator and the npm smoke runner have their own tests. These all run in the dry-run
workflow. Not exercised until the pipeline runs on GitHub: the macOS builds, the cross builds, real keyless signing and
verification against Sigstore, `gh release` steps, the Homebrew pull request, and `brew install` itself. That is why the
first thing to do is a dry run, then a pre-release tag (`v0.1.0-rc.1`), and only then a stable release.
